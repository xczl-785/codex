# 实践任务 0006：Subagent 委派、通信与生命周期

资料正文由本 Codex 学习仓库维护；实验代码、已确认的本地行为契约、实施进度和测试证据由独立 CodebaseAgent 工程维护。本文件提出学习目标与设计输入，不表示目标工程已经实现，也不替学习者预先决定控制面设计。

## 要解决的具体问题

用户要求 A 解释某个仓库的恢复机制。A 派 B 检查“历史文件缺失时会怎样”，自己检查正常恢复路径。B 有独立历史，能够自行选择只读工具；A 获取 B 的发现后，结合自己的证据汇总答案。

过程中 A 可能补充线索，也可能发现问题范围不对而中断 B，再交付修正后的任务。B 的一次答复结束后，仍可能收到后续任务。

这个场景要求把三个完成时刻分开：创建调用结束、子任务执行结束、父方完成业务整合。若把 B 当作一条阻塞工具调用，父方就难以在其执行期间协调；若只创建独立 Thread，又缺少归属、通信和结果回传规则。

## 复用与范围

复用现有 Agent 循环、Thread 历史、只读仓库绑定、Call/Output 配对、取消与持久恢复能力。子方仍是完整 Agent，不为它另写一套简化的模型—工具循环。

首轮围绕一个父方和直接子方建立闭环，再用两个子方检验结果归属和容量边界。实现语言仍用 Rust，先用 ScriptedModel、fixture repository 和可控制的 gate 验证，真实模型只作为后续体验手段。

本实践覆盖：

- 子身份与父子归属、独立历史、初始任务和受限配置；
- 普通消息与触发工作两类操作、忙闲状态下的行为；
- 结果通知、等待与状态查询，以及父方整合；
- 中断当前任务、后续派工、结束协作与资源回收；
- 重启后的事实保留和不重复执行边界。

多层递归委派、兄弟之间自由派工、任意 Thread 寻址、A2A、远程调度、durable sleep、自动空闲卸载及完整归档界面不属于本次基础验收。已学过的机制用于帮助分清边界，不要求全部复刻。A2A 继续作为[课程 0024](../lessons/0024-a2a-and-cross-system-delegation.md)的概念扩展。

## 开工前由学习者表达的设计

按目标工程 WORKFLOW，每个切片先描述正常路径、一个失败路径和一个边界场景；Agent 做轻量对抗性审查，再实现已经明确的切片。以下问题分阶段回答，不要求一次设计完整系统。

| 阶段 | 必须明确的控制面问题 |
| --- | --- |
| 创建 | 谁拥有子身份与关系？创建成功承诺到哪一步？容量按什么对象计数？部分创建失败如何释放资源？ |
| 初始条件 | 首版给子方哪些历史背景？哪些配置继承、哪些允许覆盖？权限如何保持不扩大？ |
| 消息 | 谁拥有邮箱？交付成功表示入队还是已进入模型请求？忙时在何处消费？队列满如何反馈？ |
| 触发 | 空闲时如何开工？忙时新任务是排队、并入当前执行还是拒绝？如何避免同一子方并发两个 Turn？ |
| 结果 | 结果如何关联子身份、本次任务和 Turn？父方已结束时怎样保留结果？通知重复或失败如何处理？ |
| 生命周期 | 中断返回表示请求已接收还是清理完成？父 Turn 取消、服务退出、显式关闭分别影响谁？ |
| 恢复 | 哪些关系、消息和任务事实持久化？重启后哪些只可查看，哪些可以显式续作？ |

建议首版采用显式任务与必要背景，不复制父方全部历史。若选择历史继承，必须明确它是创建时的背景快照，不能继承活动工具句柄、调用身份或把旧授权变成新授权；不能丢掉 Call/Output 的因果配对。

类型、职责和生命周期应表达同一套设计：公共 Agent 运行机制负责执行，协作层负责身份、交付与协调。同步原语与 Rust 类型在语义明确后选择，不把工具名直接当作架构，也不为复刻 Codex 的内部类型引入多套分发方式。

## 实施顺序

### M0：设计一个可观察的委派流程

学习者描述 A/B 的正常流程，指定失败与边界行为。确定身份、任务、Turn、工具 Call 和消息各自的含义，记录首版范围及开放决定。以验收材料建立事件剧本；未决定的语义不能由测试替身悄悄补齐。

### M0.5：单 Agent Steer 前置实践

先学清 Queue 与 Steer，再在引入子身份前验证公共运行循环如何接收执行中的新要求。场景是：Agent 正在分析恢复机制，用户补充“把范围缩到历史文件缺失”；通过 Steer 继续当前 Turn，后续模型请求能够看到补充内容。对照场景是将“接下来分析权限机制”排入 Queue，等待当前 Turn 结束再开启后续工作。这里的“0.5”指本实践 M0 与 M1 之间的前置切片，不另起实践编号。

学习者先表达输入准入与执行循环的职责边界：谁判断当前活动 Turn，谁保存待消费输入，谁将其纳入后续模型请求，谁处理 Turn 恰好结束的竞争。沿用公共 Agent 执行机制；不要先为子 Agent 单独实现一套 Steer，也不预先指定 channel、锁或回调结构。

前置理论与场景回顾已收束，尚未核验目标工程或启动实现。下一步先对照目标工程的 Turn 登记、输入入口、模型/工具循环、历史记录和取消机制完成职责映射。重点识别“检查仍可接收并入队”与“关闭接收入口”必须协调的业务边界；Codex 用活动 Turn 锁实现，不要求目标工程机械复制同一同步结构。工程中的验收结果才决定 M0.5 是否完成。

用户已明确选择以当前 Codex 的 Queue/Steer 功能和异常闭环为实践对照，不另行设计简化版交付语义。设计工作是把已核实行为映射到目标工程的职责和生命周期；实现可以分切片推进，但不得因分阶段而删掉失败与竞态要求。未知分支先查源码和测试，不能自行补成另一个产品契约。

行为契约：

- 严格 Steer 必须针对调用方预期的活动 Turn；空闲或 ID 不匹配时明确失败，不悄悄开新 Turn 或投给下一轮。
- 接收成功只承诺运行时接受输入；模型可见性必须通过实际请求另行证明。成功路径保持 Thread 与 Turn 身份。
- 固定消费边界与已接受输入的顺序；当前已发出的模型请求不能被当作已经包含后来补充的输入。
- Steer 不隐含取消工具或撤销既有副作用。已有 Call/Output 仍须按原有契约收口，再由模型在约定边界使用新输入。
- 对接收与 Turn 结束的竞争，明确已接受但尚未消费输入的归属，以及拒绝后调用方怎样保留输入。不能静默丢失、串入下一轮或重复消费。
- 正常循环与外层任务复查待输入并尝试在原 Turn 继续；保留 Codex 极晚输入或异常收尾时的历史记录边界，不改成“接收成功就绝对保证原 Turn 采样”。历史保存不等于模型已读。
- 客户端与严格 Core 分层对照：NoActiveTurn 后转新 Turn，ID 不匹配更新目标并重试一次，不可 Steer 时保留为拒绝后的待发输入；重复失败与中断恢复按已核实路径处理。客户端另一次提交不能记成原严格 Steer 成功。

用 ScriptedModel、工具 gate 和请求捕获实现[前置验收](materials/0006-subagent-lifecycle-acceptance.md#m05-前置验收单-agent-steer)。Queue 的后续工作等待队列与 Steer 的当前 Turn 待消费输入分别表达；不要求复制 Codex 的 TUI 结构。本轮仍为学习与资料准备，未启动目标工程实现。

用户明确将客户端与独立 App Server 之间的传输断线恢复排除在本实践之外：不要求增加服务端部署、重连、Unconfirmed 队列协调或跨连接交付保证。这部分保留为课程中的架构扩展知识，不作为 M0.5 退出条件。已有正常运行中的输入保留、中断恢复和记录回执协调仍在范围内；这里的范围收束不改变严格 Steer、结束竞态或取消契约。

退出时，学习者应能解释“接收成功”和“模型已经看见”的差别，以及为什么 Steer 不能替代 Interrupt。目标工程记录验证证据后，再进入 M1；M2 复用这里的忙时输入能力，但普通消息、唤醒空闲子方和协作结果归属仍须另行设计，不能把所有通信操作直接等同于 Steer。

#### 为什么用 gate，而不是只看日志

gate 是测试控制的暂停点，不是新增产品功能。让模拟只读工具停在返回前，确认 T1 仍在运行；此时提交 Steer 并观察接收结果，再释放 gate，检查下一次发给 ScriptedModel 的请求是否包含补充、Turn 是否仍为 T1、原工具 Call/Output 是否完整。这样能够稳定制造“执行过程中到达输入”的时机，避免靠手速或 sleep 猜测。

对照测试把同一输入改为 Queue：T1 的后续请求不提前包含它，正常结束且允许发送后才由它启动 T2。Trace 记录发生过程，受控测试则安排顺序并断言结果；两者可以配合，不能用一条“发送成功”日志替代请求内容与身份的断言。

### M1：创建与独立执行

复用公共运行循环，建立父子关系并交付初始任务。用 gate 保持 B 未完成，证明 A 已收到创建结果并能继续工作。校验独立历史、仓库绑定、配置边界、创建失败清理和名额释放。

### M2：通信与结果闭环

实现普通消息、触发工作、状态查询与有界等待。通过捕获模型请求验证“消息被接收”和“模型实际看到”是两个事件。B 的完成结果回到 A 后，由 A 整合；多个子方的结果必须关联正确任务。

### M3：中断、后续任务与关闭

复用既有取消机制，区分请求停止与完成清理。中断后能够按契约给同一 B 派新任务，旧执行的迟到结果不能污染新任务。确定父 Turn 结束、取消和显式关闭的不同后果；关闭释放资源并保留历史，不撤销已经发生的事实。

### M4：恢复与实践收口

在任务运行中和结果已产生两个位置模拟重启，验证持久边界。基础要求是保留已承诺的事实、标记未完成或未知结果且不静默重放任务；跨重启自动继续协作不是默认要求。最后在目标工程更新契约、能力文档、测试索引和 STATUS，并复核学习者理解。

## 验收与完成

详细场景和观察字段见[验收材料](materials/0006-subagent-lifecycle-acceptance.md)。不能用真实模型偶然回答正确、日志写着 Running 或固定延时证明生命周期正确。

学习者应能解释：为什么子 Agent 需要自己的执行循环；为什么消息成功不等于开始工作；一次工具返回与子任务完成有什么区别；中断、关闭、历史保留分别改变什么；重启后为什么不能无条件重做旧任务。

资料准备完成不等于实验通过，专题已学完也不等于全部失败分支已经掌握。实际验收证据归目标工程，这里只在收到实践反馈后补充学习记录。
