# CodebaseAgent TUI 间距与视觉边界：调研及后续改进参考

调研日期：2026-10-21。

本文为 CodebaseAgent 后续登记 deferred、独立讨论与实施提供背景和证据，暂存于实践目录的改进调研类别，不属于课程或编号实践契约。当前确认的约束是继续使用 Ratatui、尽量控制改动范围；下述方案是推荐方向，具体布局和值尚未通过视觉样例确定。本轮只形成文档，没有修改 CodebaseAgent 源码、登记其 deferred 或验收任何界面改动。实施状态与启动时机由 CodebaseAgent 自己的状态文档维护。

## 1. 问题与目标

用户最初比较 Codex、CodebaseAgent、OpenCode、Claude Code 的 TUI 框架，真正关心的是：CodebaseAgent 中文本与区域之间的间距不容易调得精细、自然，尤其纵向经常出现“不留空行太挤，留一行又太空”。

输入框顶部、底部文案是代表性例子，不是问题的全部范围。应一并考虑消息、工具过程、状态区、提示区、输入区、弹窗中出现的同类间距关系；不要求一次重做所有界面。

目标包含两个不同维度：

| 维度 | 希望改善的结果 | 在常规 Ratatui 中的边界 |
| --- | --- | --- |
| 调整的自由度 | 区域内外间距、文本分组、对齐和装饰可以独立理解和调整 | 可以通过轻量布局整理改善 |
| 调整的精度 | 普通文字能移动半行或几像素，局部间距不必以整行为步长 | 常规字符网格布局不能提供 |

后续不能把第一项的改善描述为第二项已经解决，也不能因为第二项有硬限制，就忽略现有布局仍可改善的部分。

本次探索不启动框架迁移、终端渲染器重写、运行时重构或像素图形协议接入。也不把固定某一种终端、修改用户全局字体与行高作为默认解决方案。

## 3. 框架比较中需要保留的结论

| 工程或路线 | 已核实的基础 | 与本问题直接相关的结论 |
| --- | --- | --- |
| Codex CLI | Rust、Ratatui、Crossterm，并定制终端管理 | 普通文字布局仍以整数行列计算；定制刷新与历史管理不等于像素排版 |
| CodebaseAgent | Rust、Ratatui 0.30.2、Crossterm 0.29，使用 Ratatui `Terminal` | 当前存在整行留白和多处局部 padding；可以整理控制位置，但不能产生任意半行文本坐标 |
| OpenCode TUI | TypeScript、SolidJS、OpenTUI | JSX/Flexbox 提高布局表达便利，文字仍绘制到字符网格；输入框源码也使用整数 padding |
| React/Ink 路线 | React 组件体系与终端渲染 | Ink 明确以字符列和行定义尺寸；类似 CSS 的写法不等于 CSS 像素单位 |
| Claude Code | 早期使用 Ink，后续公开说明重写渲染系统并保留 React | 当前内部实现未完整核实，不能用通用 Ink 的表现代替它，也没有证据证明其普通文本采用任意像素间距 |

此前关于性能、占用和开发复杂度的比较，只适合保留为条件性判断：Rust/Ratatui 没有 JS 引擎基线，便于显式控制工作量；Solid/OpenTUI 和 React/Ink 更便于复用组件化开发方式。实际成品的资源消耗取决于历史、缓存、排版和刷新策略，不能据此给应用排名。对于本次问题，排版坐标精度比这些一般性优缺点更直接。

## 4. 字符网格为什么造成间距困扰

常规终端文本定位使用“第几行、第几列”。字符格的实际像素大小由宿主终端的字体、字号、行高等决定。

假设字符格高度是 20px，那么增加一行留白约增加 20px，而不是可以任选 4px、6px 或 10px。此数值仅为解释示例，不是当前机器的测量结果。字符格通常高于宽，因此纵向留白的跳变尤其明显。

Ratatui 的 `Rect` 和 `Padding` 使用整数尺寸；`Padding` 四边为 `u16`。比例布局、百分比或更复杂的布局计算，最终也不能让常规文字自由落在半行位置。

需要严格区分：

1. **文本位置**：文字所在的行列，受字符网格限制。
2. **视觉边缘**：背景、边框、阴影在字符格内部呈现的形状，可以通过特殊字符做得更细。
3. **屏幕物理尺寸**：字体和行高改变一格有多大，由终端环境决定。

## 5. 具体源码发现

### CodebaseAgent

调研时的 `src/tui.rs` 总布局采用 `Layout::vertical`，分别分配正文、模型摘要、待发区、输入区和帮助区等区域；输入区高度使用 `input_lines + 2 + feedback_height` 一类表达式。

局部绘制中可见 `Padding::new(2, 2, 1, 1)`。帮助区则根据区域高度计算上下 padding，再绘制文字。这说明最终留白由外部分配高度和内部绘制共同决定；它不是缺陷证明，但意味着调整时需要追踪多个位置。

核对入口：`D:\Program\AgentLab\CodebaseAgent\Cargo.toml`、`src/tui.rs` 中的 `draw`、`draw_input`、`draw_help`。调研时相关位置约为 3610、4574、5241 行。

### Codex

`custom_terminal.rs` 派生自 Ratatui Terminal，主要证据支持其终端输出、历史、视口和光标管理存在定制，不能据此推断文字间距精度更高。

输入框 `layout_with_options` 使用整数 `Constraint` 和 `Insets::tlbr`，包括顶部 `1 + voice_rows`、底部 `1` 的留白。共享几何计算用于保持测量、绘制和光标一致，这一做法适合作为本工程的参考。

源码入口：

- [输入框几何计算](../../../codex-rs/tui/src/bottom_pane/chat_composer/composer_layout.rs)
- [Insets 定义](../../../codex-rs/tui/src/render/mod.rs)
- [定制 Terminal](../../../codex-rs/tui/src/custom_terminal.rs)

### OpenCode

调研时的输入框使用 `paddingTop={1}`，左右 padding 根据宽度取 1 或 2，并配合背景色、`┃`、`╹` 等边缘字符。它提供了在网格内组合视觉层级的实例，没有证明文本能够按像素定位。

## 6. 其他使用者的做法及适用边界

| 做法 | 直接证据或例子 | 能改善什么 | 不能承诺什么 |
| --- | --- | --- | --- |
| 网格内重新组织视觉层级 | OpenCode 输入框的背景、侧边字符与整数 padding | 厚重边框、重复留白、分组不清 | 任意半行文本间距 |
| 半块或象限字符装饰 | `ratatui-garnish` 的 `HalfShadow`；Ratatui 比例边框 | 背景边缘和阴影的细腻程度 | 普通文字随边缘一起移动半格 |
| 调整终端行高 | WezTerm `line_height` | 全局疏密与字形观感 | 应用内每个区域独立指定像素间距 |
| 像素图形协议 | Kitty graphics protocol | 像素图形与位置控制 | 自动保留普通文本选择、复制和命中行为 |
| 特殊文字尺寸协议 | Kitty text sizing protocol | 支持环境中的文字缩放和格内对齐 | 通用 CSS 布局，或无需适配即可使用 |

这些是可核对的实践和能力实例，不是行业采用比例调查。

半块字符如 `▀`、`▄`、`▌`、`▐` 可以用前景色与背景色形成半格视觉边缘。但占用的布局仍是完整格子。文字与边框的距离感可以改变，两段普通文字的基线距离不会因此获得任意精度。

Kitty 文字尺寸协议提供普通大小文字上下各留半行空白的示例，说明“终端绝对无法做到”过于笼统；但其分数缩放不改变占用格数，仍要求终端支持及应用适配。本次推荐方案不依赖该能力。

## 7. 推荐方案：轻量整理间距与视觉边界

### 7.1 为每一段空白确定一个控制位置

| 布局关系 | 建议责任归属 |
| --- | --- |
| 两个相邻区域之间的间隔 | 共同父布局 |
| 区域边缘到内部文字的留白 | 该区域自身 |
| 同一区域内文字或内容组的间隔 | 该区域内部布局 |
| 边框、色块收边、阴影 | 装饰绘制 |
| 内容起始列与对齐关系 | 明确的内容几何规则 |

避免同一段空白由上一区域底部 padding、父布局 gap、下一区域顶部 padding 共同叠加。实施前先确认实际来源，不预设当前所有位置都存在重复。

### 7.2 按内容关系集中少量间距规则

优先整理重复使用且需要调校的关系，如组内文本、组间隔、区域内边距、内容缩进、装饰占用。具体数值由视觉样例确定，不要求统一成一个全局间距，也不建立几十个用户配置项或一套通用布局引擎。

可采用的初始原则：

- 同组主次文字可以连续排列，结合明暗表达层级，不机械插入空行。
- 独立内容组需要分隔时，由明确的一处控制。
- 横向缩进与纵向留白分别设计，不要求四边数字相等。
- 可选内容消失时，其专属留白也消失；确需保留位置以稳定画面的场景应明确说明。
- 小窗口优先压缩装饰性留白，保留输入和必要反馈；不要让各子区域互不知情地各自压缩。

### 7.3 分离文本几何与装饰绘制

先用减少嵌套边框、背景分区、侧边标记、共享分隔线改善厚重和松散感。仍不协调的少数背景边缘，再尝试半块收边或轻量阴影。

半块装饰是可选局部尝试，不是默认全局样式；避免为此引入复杂渲染层。它适合调节可见边缘，不能作为半行文字布局的替代承诺。

### 7.4 测量、绘制和交互复用几何计算

调整区域时，将内容宽度、高度、内边距和必要的子区域计算收在一处，让换行测量、绘制、输入光标及鼠标命中使用一致结果。

只整理本次触及的区域，不要求重构整个 TUI。这里借鉴 Codex 的共享几何原则，不复制它的全部终端层或目录结构。

## 8. 后续实施节奏与验收建议

以下是 deferred 激活后的建议步骤，不是本轮已启动的实施任务。

1. 在相同终端、字体、字号和窗口尺寸下取得代表性画面，标注具体不舒服的距离。覆盖消息、工具过程、输入与提示、弹窗等不同关系，避免只修输入框上下文案。
2. 对选中位置区分重复留白、对齐问题、装饰厚度、网格精度限制，确定各段间距的责任。
3. 先调整现有布局与留白，再针对残余问题尝试少量装饰变化。保留可比较的前后画面。
4. 检查窗口缩放、多行内容、可选提示出现和消失等状态，并由用户确认观感。

验收应同时包含视觉与行为：

| 场景 | 需要确认 |
| --- | --- |
| 常规窗口下的典型界面 | 主次层级、组间距离、起始列协调，没有无意叠加的留白 |
| 窄窗口、低高度窗口 | 按明确优先级压缩，关键内容可读，没有重叠或越界 |
| 输入从一行变为多行 | 换行宽度、高度、光标、鼠标命中一致 |
| 提示、待发内容出现或消失 | 所属区域和留白符合预期，不残留无意义空行 |
| 流式输出、展开与折叠 | 几何变化不破坏既有阅读位置和输入行为 |
| 半块或细边缘装饰 | 在项目实际支持的终端和字体组合上可接受，必要时有简单退化样式 |

纯视觉选值不能只靠快照断言证明“好看”；应查看真实终端。行为变化则按目标工程规范补充相关测试，不为调色或静态留白机械增加大量测试。

停止条件：所选区域的间距可以从明确位置调整，观感经用户确认，相关交互没有退化。若剩余要求主要是普通文字任意半行或像素位置，应保留为已知能力限制，不通过持续堆叠装饰补丁伪装解决。

## 9. 可用于登记 deferred 的摘要

**建议名称：** Ratatui 文本与区域间距、视觉边界优化。

**问题：** 当前界面不同文本和区域的疏密关系不易调校，纵向受整行步长限制，部分留白需同时理解外部高度与内部 padding。问题覆盖消息、工具过程、状态、提示、输入和弹窗等区域，输入框上下文案只是例子。

**约束与方向：** 保留 Ratatui，控制改动范围；先用代表性画面定位问题，明确区域间距与内部留白的归属，集中少量语义化间距规则，统一测量、绘制和交互几何；按需用背景、侧边标记和半块装饰改善视觉边缘。

**边界：** 不承诺普通文字的任意半行或像素排版，不默认更换框架、重写终端层或依赖特殊终端协议。

**启动时机：** 由 CodebaseAgent 工程单独安排，本调研不改变其当前任务。

**完成依据：** 选定场景的真实终端前后对照获得用户确认；窄窗口、多行输入、提示显隐、光标与命中等行为保持正确。
