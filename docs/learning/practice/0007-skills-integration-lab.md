# 实践任务书 0007：Skills 接入体系

## 文档用途与决策归属

本任务书将本次 Skills 课程转为独立 CodebaseAgent 工程可使用的实践输入，完整交代机制、设计问题、Codex 对照与验证场景。学习者已通过专题整体回顾，要求开始准备实践材料。

**本文件不约定实现范围，不划定 MVP、必做项、排除项或延期清单，也不安排实施阶段。** 下文按职责组织知识，不表示优先级或要求逐项复刻。CodebaseAgent 工程根据实际场景确定实现内容、契约、依赖、阶段和验收要求；本文件中的验证场景供确定当地范围时选取与细化，不构成全量交付门槛。

| 事项 | 归属 |
| --- | --- |
| 已学机制、源码依据和实践问题 | 本学习仓库及本任务书 |
| 实现范围、设计选择、实施计划 | CodebaseAgent 工程结合实际场景确定 |
| 当前能力、权限状态、接口和 Provider 支持 | 目标工程当前源码、配置及工程文档 |
| 实现、测试、交付与体验验收证据 | 目标工程维护，本文件不镜像实时进度 |
| 课程反馈与后续教学衔接 | 本仓库 MAINTENANCE 和学习记录 |

目标工程为 `D:/Program/AgentLab/CodebaseAgent`。接手时读取该工程自己的 AGENTS、工作流、状态和能力资料，再将本任务书映射到实际系统；本次未审计其当前实现，不据历史课程断言某能力已接入。权限沙盒实验完成也不能等同于已正式集成到 CodebaseAgent。

既定学习顺序仍为：Skills 课程与回顾 → Skills 接入实践 → 在本学习仓库开展 CodebaseAgent 转型课程 → 学完再准备转型实践任务书 → 独立工程实践。本次不提前启动转型课程；这条教学安排不替目标工程划定 Skills 的实现范围。

## 一、贯穿场景与预期学习结果

用户要求 Agent 分析一个代码库的崩溃恢复机制。存在 recovery-analysis Skill，提供持久事实、内存投影、写入边界、重放与外部副作用的分析方法。用户可以显式指定，也可以只提出任务，由模型根据候选描述选用。Agent 读取正文，按需取得引用资料，使用实际可用的工具，最后交付带证据和不确定性说明的结论。

在此场景上引入同名、禁用、文件变化、读取失败、工具不可用、压缩、重启和子 Agent 委派，可以观察 Skill 如何贯穿现有 Agent 系统。

实践应帮助学习者解释：Skill 怎样改变模型的方法；宿主提供什么接入能力；正文如何进入模型请求；工具执行如何继续受工程契约约束；发现、选择、读取、使用记录和任务成功为什么不是同一状态。

## 二、主循环接入相关内容

```text
用户输入 + 当前配置/环境
  → 取得候选清单
  → 解析显式选择，或向模型展示可选方法
  → 读取所需正文与资源
  → 组织模型上下文
  → 模型提出工具调用
  → 现有工具运行时执行并记录结果
  → 后续采样、补充输入或任务结束
```

这是一条职责链，不要求建立一套与现有循环平行的 Skill 执行器，也不预先指定类名、继承结构、回调体系或扩展框架。

### 2.1 发现、元信息与资源身份

涉及名称、description、正文位置、来源、启用状态、隐式调用策略、发现诊断及排序。清单提供选择依据，不等于所有正文已加载。

本地发现涉及扫描根、cwd 与项目边界、根内递归、深度和数量限制、路径规范化及重复资源。同路径重复与不同路径同名应分别讨论。当前 Codex 本地合并按正文路径去重，不是统一按名称覆盖。

Project/.agents/skills 与 Project/module/.agents/skills 是不同扫描根。项目祖先链依据发现用 cwd；从 Project 开始不等于向下发现所有模块的 Skill，任务读取了 module 文件也不等于改变发现 cwd。

目标工程需结合实际工作区模型决定来源、身份和可见性语义；上述 Codex 行为是对照，不是预先规定目标工程必须采用的规则。

### 2.2 用户输入与选择

区分文本中的 `$name`、客户端绑定路径的结构化选择、模型自主选用。界面显示相同名称不代表底层输入相同；客户端也可能把手打 mention 转成结构化输入。

设计问题包括：同名怎样消歧，禁用怎样反馈，失效绑定是否拒绝，选择是否与特定清单快照绑定，以及重复选择如何处理。显式目标失效时，不应在用户不知情的情况下换成另一资源。

当前 Codex Core 所用选择器先匹配结构化路径，再处理文本；它与扩展选择器的裸名称行为不能不加区分地概括为同一规则。

### 2.3 正文与辅助资源加载

涉及读取、编码、解析错误、缺失资源、长度预算、来源标记及同次输入的重复注入。声明“已使用”应与实际读取或执行证据对应。

name/description 帮助选择；正文提供共同方法与关键约束；references 保存分支知识；scripts 提供机械处理；assets 支持输出产物；agents/openai.yaml 提供可选宿主/UI、依赖和策略配置，不是 Subagent 创建开关。

正文引用应相对包及所属来源解析，不能默认相对工作区。辅助文件不因存在于目录里就全部递归注入。脚本读取、脚本执行和依赖安装是不同动作。

元信息快照不必然冻结文件内容。若先发现后读取，期间文件可能改变；是否记录内容版本、冻结正文或接受读取时最新内容，属于目标工程的一致性设计。

### 2.4 模型请求与工具往返

候选清单和已选正文应有不同角色。当前 Codex 显式正文可构造成带 `<skill>` 标记的 user 消息；模型通过普通工具读取时，正文通常位于工具结果。目标工程依据自己的指令层次和 Provider 契约设计承载，不机械复制角色。

Responses 中 function_call 与 function_call_output 是独立条目，用 call_id 关联；arguments 是 JSON 字符串。它们不能与 Chat 的消息结构混用。客户端 UserInput::Skill 是选择信息，不是原样送给模型的正文。

接入位置应结合现有用户输入、Turn/Step、工具循环、Steer、取消和历史收口判断。选择、读取或等待资源期间发生取消，或运行中补充新的 Skill 要求时，需要说明何时进入后续请求，不能静默丢失或跨轮误用。

## 三、上下文与生命周期相关内容

| 对象 | 要区分的问题 |
| --- | --- |
| 当前文件 | 保存的最新内容是什么 |
| 发现快照 | 知道哪些候选及其元信息 |
| 本次选择 | 用户或模型选用了哪些资源 |
| 历史正文 | 已经读入哪些具体内容 |
| 当前请求 | 模型此次实际看到什么 |
| 使用事件 | 系统识别到什么行为，发生在执行前还是执行后 |

多次采样可以复用历史正文，不意味着每次重读；跨 Turn 仍可见不等于当前任务仍适用。文件 V1 改为 V2，不自动替换历史 V1。禁用或删除不等于撤回已读文本。

压缩和恢复需检查最终历史、保留信息及必要重读。重新建立候选清单不等于恢复全部完整正文；历史中有调用事实不等于应再次执行脚本。持久化哪些身份、版本、诊断与事件，需与目标工程既有恢复模型协调。

目录预算、正文预算、工具输出截断和总上下文预算属于不同位置。静默截断关键要求可能造成错误行为；具体阈值和超限策略由工程场景决定，Codex 各来源规则不是统一常量。

## 四、Codex 的细节增强与实现对照

本节保留课程涉及的增强机制及设计动机。“增强”是知识分类，不代表本次排除、延期或降低优先级。

| 机制 | 解决的问题 | 映射时需要考虑 |
| --- | --- | --- |
| 文件监听与缓存失效 | 外部新增、修改、删除后刷新发现结果 | 文件事件、路径匹配、节流、粗粒度清缓存；不等于内容哈希逐个比较 |
| 快照与稳定身份 | 一次处理使用明确候选，关联路径及来源 | cwd/config 缓存、规范化与逻辑发现路径、内容变化窗口 |
| Core/扩展注入协调 | 多条来源路径可能提供同一正文 | 正文去重与使用事件去重是不同集合和生命周期 |
| world state | 向模型同步当前环境与能力变化 | 比较基线、更新消息、持久记录、缺失基线与新窗口；清单变化可发送整段内容 |
| 提示缓存友好的组装 | 减少不必要的前缀变化 | 请求重建不等于内容变化；原地改写和尾部追加影响不同；实际看 cached_tokens |
| 增量工具声明 | 工具变化通过历史条目表达 | AdditionalTools、命名空间、定义哈希、变化/移除提示；当前 Codex 的 Lite/功能开关条件 |
| 基础指令状态更新 | 在支持模式中保留前缀并同步指令变化 | 模型/指令哈希、初始声明、压缩后重建 |
| 隐式使用识别 | 把普通读取或执行请求关联到已知 Skill | 命令识别覆盖面、Turn 内去重、事件时刻；不证明执行成功 |
| 扩展消费使用事件 | 统计、插件归属、选择实验和审查证据 | 哪些消费者启用、来源校验；不提供权限豁免 |
| 启用与隐式策略 | 区分禁用和仅显式使用 | 默认清单、显式选择、历史正文及文件权限分别处理 |

world state 的思想可用于不同 Provider；Codex 的 AdditionalTools 载体不能直接照搬到标准 Chat 消息。标准 Chat 可以更新顶层 tools 和追加状态消息。上下文增量、网络传输增量、服务端提示缓存不是同一机制。

## 五、执行、组合与来源扩展

### 5.1 工具和权限

Skill 提供方法，不授予权限。脚本仍依赖解释器、工具、文件/网络权限和环境。可读、可执行、可写回安装目录是不同条件；Skill 所需工具可能根本未接入。能力缺口、审批拒绝、执行失败与方法不适用要分别表达。

AGENTS.md 提供项目约定，Skill 提供任务方法，工具/宿主负责必须强制保证的行为。具体权限机制是否进入本次工程实现，由目标工程决定；不能把已有独立权限实验视为正式接入的证据。

### 5.2 多 Skill 与 Subagent

多个 Skill 可按输入输出组合，如恢复分析交付证据，文档 Skill 整理成果。正文都已注入不代表冲突已被程序解决；加载顺序不自动形成优先级。

对子 Agent 分别检查历史正文继承、自身候选发现与读取、实际工具权限。父方用过不代表子方可访问，未继承历史也不代表子方不能自主发现。角色限制、工作目录、资源环境和历史模式都可能影响结果。

### 5.3 插件、执行环境和远端

插件是打包交付维度，本地/远端是访问维度。安装在本地的插件 Skill 可以通过文件读取；依赖声明不等于能力已接入或授权。

Codex 用 authority、package、resource 与读取 context 保持来源边界。authority 是路由归属，不是更高指令权限。不透明资源 ID 不应被当作本地路径；引用资料要在正确来源和包中解析。环境失效、连接不可用和远端缓存刷新需要明确失败与一致性语义。

## 六、Skill 本身的设计与效果验证

选择实际任务编写或采用 Skill，观察是否改变了有价值的判断。description 说明能力及适用场景；正文保留共同方法、关键条件和资料路由；references 渐进读取；scripts 承担输入输出明确的机械工作。短小单一任务不需要为了形式拆出辅助目录。

约束强度对应偏离的后果，不把特定仓库路径和偶然案例写成普遍流程。比较无 Skill 与使用 Skill 的结果：是否更容易找到正确证据、识别关键失败、报告不确定性，而不是只看输出更长或步骤更多。

## 七、可选取并细化的验证场景

下表用于在目标工程形成当地验收，不是全部必须实施的列表。是否采用、预期行为及完成证据由当地范围决定。

| 场景 | 要观察的事实 |
| --- | --- |
| 显式选择一个有效包 | 选中身份、读取正文和实际请求是否一致 |
| 不显式指定但任务匹配 | 模型是否据描述正确选用；无关任务是否误触发 |
| 同名不同路径、同文件多入口 | 名称歧义与身份去重是否分开处理 |
| 禁用、仅显式、选择后文件消失 | 策略与失效反馈是否明确，是否错误替换目标 |
| 包格式错误、正文过长、引用缺失 | 诊断、预算与降级结果是否可理解 |
| 新增/删除/修改后多次请求 | 发现缓存、清单、正文版本和历史是否按契约变化 |
| 工具调用与用户多轮交替 | 消息角色、call_id、正文位置及重复注入是否正确 |
| 运行中补充 Skill 要求或取消 | 接收、读取、注入与结束边界是否协调 |
| 压缩、恢复或重启 | 保留什么、何时重读、是否误重放工具操作 |
| 脚本或依赖工具不可用 | 是否报告能力缺口而非声称成功 |
| 记录了隐式使用但执行失败 | 是否保持事件时刻与成功状态的区别 |
| 子 Agent 不继承历史或禁用某包 | 内容、发现与权限是否独立判断 |
| 远端来源断开、同名本地资源存在 | 是否坚持来源路由而非误读本地替代品 |
| 清单/工具定义变化 | 更新内容、基线、实际请求与缓存指标是否可解释 |
| 同时采用两个 Skill | 职责能否组合，冲突是否按有效要求处理 |

确定性解析、输入选择、消息序列和失败路径适合 fixture、ScriptedModel 与请求捕获；并发变化可用可控 gate。模型自主选择与任务效果需要实际任务观察。测试方法是工具，不预设工程的阶段划分。
