# 学习记录 0013：取消与进程生命周期边界

用户已经能够区分 Turn/Task 的停止、工具调用的终态和工具创建的真实进程生命周期。后续可以直接进入可控 Harness 的取消传播实践，但仍需用实现测试巩固结果与取消的竞争点。

## 理解证据

- 用户能解释取消请求发出后 Turn 正在趋向停止，工具和外部进程需要时间观察信号，不能假设所有对象瞬间同时终止。
- 用户理解任务句柄的 `abort()` 与 `SessionTask::abort()` 面向不同对象：前者请求停止异步任务，后者给具体任务额外清理机会，默认不代表强制终止全部外部资源。
- 用户主动追问进程为何进入管理器、谁决定其生命周期，并最终接受决定取消策略的是执行模式契约，而不是 Agent 根据命令文本猜测它像不像服务器。
- 在完成竞态场景中，用户正确判断：配置修改可以已经完成，整个 Turn 仍然停止，而后续验证步骤没有执行。
- 用户最初把已返回 `session_id` 的 Interactive 调用判断为 aborted；经纠正后准确复述为“工具调用已经完成，后台进程还在继续”。

## 对后续教学的影响

- 取消实践必须分别观察取消意图、工具结果、Turn 终态和外部进程，不能用一个 `cancelled` 标志代替全部状态。
- 需要重点验证完成结果不会被稍晚到达的取消覆盖、未完成调用如何显式收口，以及取消后为何不能继续采样模型。
- 暂不扩展到操作系统级通用进程树治理；先在 CodebaseAgent 中用可控模型和工具替身建立取消不变量。
