从一句话到一次 Turn

第一课不追函数细节，只建立一个可用的骨架：你在 Codex 里输入一句话后，哪些角色依次接手？

这一课的胜利条件

读完后，你能不看源码，说出“界面、App Server、Thread、Turn”各自负责什么。

先把 Codex 想成一间工作室

你看到的 TUI 是前台；App Server 是统一接单口；Thread 是一张长期保留的工作台；Turn 是这张工作台上的一轮任务。真正与模型交流、调用工具和保存状态的工作发生在后面几层。

1. 前台接话 CLI 选择交互模式，TUI 收集你的文字、当前目录、模型和权限设置。
2. 统一接单 App Server 接收 thread/start 或 turn/start 这类请求，屏蔽本地与远程差异。
3. 工作台开工 ThreadManager 找到或创建 Thread，核心运行时启动这一轮 Turn。
4. 结果回流 模型输出、工具调用、审批和完成状态以事件形式返回界面并写入记录。

Thread 和 Turn 为什么要分开？

因为“一段长期会话”和“其中的一轮工作”生命周期不同。Thread 可以存在很久，可以恢复、派生，也可以包含很多轮；Turn 通常只对应一次输入触发的工作过程。

Thread：工作台

保存身份、历史和长期状态。关闭程序后，它仍可能从记录中恢复。

Turn：这一轮

接收本轮输入，进行模型与工具循环，最后完成、中断或失败。

一个容易踩的坑

不要把 Thread 理解成操作系统线程。这里的 Thread 是产品领域里的“会话工作单元”，不是 CPU 调度概念。

第一次只认七个代码路标

  1. cli/src/main.rs 是总入口。默认没有子命令时，它会进入 TUI。
  2. tui/src/app_command.rs 定义界面内部想做的事情，例如发起一轮用户输入。
  3. tui/src/app/thread_routing.rs 把界面命令路由为 App Server 的 Thread/Turn 请求。
  4. turn_processor.rs 处理 turn/start，把 API 请求送入核心。
  5. core/src/thread_manager.rs 管理 Thread 的创建、恢复、派生和关闭。
  6. core/src/codex_thread.rs 是向某个 Thread 投递操作、接收事件的句柄。
  7. core/src/session/handlers.rs 是核心消费操作、推进 Turn 的重要处理入口。

现在不需要逐个读完。第一次源码浏览只需打开这些文件，找到对应名字，确认“它确实在这里”，然后退出。

30 秒回忆练习

先不要往下展开：如果用户连续输入三次，通常是几个 Thread、几个 Turn？App Server 又扮演什么角色？

核对答案

通常仍是一个 Thread，里面产生三轮 Turn。App Server 是统一接单和翻译请求的接口层，不是模型本身，也不是长期会话本身。

本课的一句话总结

Codex 不是“界面直接问模型”，而是界面通过统一接口把一轮工作交给某个长期 Thread，核心完成模型与工具循环，再用事件把过程和结果送回来。
