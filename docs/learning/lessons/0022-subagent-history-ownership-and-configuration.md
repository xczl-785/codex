## 从委派关系理解 Subagent

Subagent 要解决的问题是：一个 Agent 怎样把任务的一部分交给另一个能够自主推理和调用工具的 Agent，并继续协调、接收和整合结果。子方需要自己的历史与执行循环，因此复用完整 Thread 基础；同时需要父子归属、任务交付、消息、状态和结果通知，因此在公共运行机制上增加协作规则。这是依据当前实现归纳的设计模型，不冒充原作者完整设计文档。

例如用户让 A 分析数据库恢复机制，A 派 B 检查数据库缺失分支。B 自己决定查哪些文件、如何验证，A 仍负责整合答案。与之对照，用户让 A 在 App 中新建一个独立 Thread，供自己以后研究数据库，是建立新的用户工作入口。谁发起创建，不自动决定谁拥有后续协调关系。

| 维度         | 创建供用户继续使用的独立 Thread | 创建 Subagent                        |
| ------------ | ------------------------------- | ------------------------------------ |
| 目的         | 独立开展一个主题                | 承担父方任务的一部分                 |
| 后续工作安排 | 用户可进入该对话继续安排        | 通过 Agent 协作机制安排              |
| 关系         | 创建关联本身不证明父子归属      | 明确保存父 Thread 和协作身份         |
| 结果处理     | 创建本身不保证通知创建者        | 当前实现具有向父方发送终结通知的机制 |

这里的 App 列按用户描述的功能效果比较，尚未定位其专用工具实现，不能断言其内部调用哪一个接口。复制历史、继承配置、由 Agent 发起创建，都不能单独作为 Subagent 身份的判据。

子 Agent 也走公共 Thread 启动和工具装配流程。继承的是启动所需条件，而非父方全部活跃工具对象、进程句柄或执行现场。同一工作区不能保证会话环境相同：父方当前客户端扩展、环境选择和配置覆盖可能超出磁盘默认设置。继承这些条件，使委派任务延续当前实际工作条件；角色和显式配置再在规则允许的范围内调整。

## 一次 spawn_agent 怎样落实委派

以任务名称 check_recovery、消息“检查数据库缺失处理路径，给出源码依据，先不改代码”、fork_turns=none 为例。名称负责寻址，消息负责本次任务，历史选项负责背景范围，三者分别生效。

1. 工具处理器解析参数，公共创建入口检查消息非空，准备子配置；根据父方路径拼出 /root/check_recovery，并构造含父 ThreadId、深度和角色的 ThreadSpawn 来源。归属由运行时建立，不依赖模型记住提示词。
2. 创建后端检查容量并预留名额，准备环境、插件选择等条件。需要继承历史时，读取并过滤父方上下文；不继承历史也仍可继承工作条件。
3. 调用 spawn_child_thread，进入公共 spawn_thread，创建子方运行体。之后安排父子关系持久化并等待相应步骤；继承历史时还处理初始 rollout 的物化。不能把这段等待扩大解释为所有存储失败都会强制阻止创建，具体错误策略需逐项核对。
4. 向子方提交初始任务。原生 V2 创建入口把消息标记为 MessageDeliveryMode::TriggerTurn，所以创建操作包含触发执行的任务交付，不只是留下背景消息。这与 followup_task 使用相同的交付模式概念，不表示内部调用了 followup_task 工具。
5. 输入接收后，完成创建登记并返回 Agent 信息；工具层返回任务名称等信息，供父方继续协作。返回不等待业务任务完成。

```text
准备配置与归属 → 检查容量、准备环境和历史 → 创建子 Thread
    → 处理关系与历史持久化 → 提交触发执行的初始任务 → 创建返回
                                      ↓
                              B 独立推进模型—工具循环
```

运行时决定是否启动执行；B 的模型看到任务和上下文后决定具体做什么。创建返回时 B 可能尚未开展具体调查，也可能已执行若干步骤，短任务甚至已经结束；接口不保证返回时的业务进度。ThreadSpawnResult 的源码注释明确指出，接受创建不等于 Turn 已完成。

创建 Thread 与提交首个任务是两个职责，可以组合为一个工具。普通 App 新建 Thread 也可以组合这两步；Subagent 另外把它们纳入明确的归属和协作规则。

## 历史来源和控制归属是两种关系

普通用户 Fork 创建新的对话分支，拥有历史来源关系；Subagent 创建还建立父 Thread、Agent 路径和任务汇报关系。不复制历史也能创建子 Agent，复制历史也不自动创建父子协作关系。

完整历史派发会先 flush 父方日志；当前分页路径读取最新模型上下文，不保证重新装入 UI 中所有旧原文。父方已有压缩时不能凭 fork_turns=all 恢复压缩前全部原文。它不复制运行中 Task、工具会话或进程句柄，创建后的父消息也不自动持续同步。

## 默认历史过滤的具体含义

默认 preserve_fork_prefix=false。记录类型和指令片段标记控制过滤，并非模型自由判断重要性。

| 内容                                               | 默认处理                                                       |
| -------------------------------------------------- | -------------------------------------------------------------- |
| 用户消息                                           | 保留并标记为继承背景，不能重新登记为子方本地用户授权           |
| PartialAnswer / FinalAnswer 阶段的 assistant 消息  | 保留，可作为已形成结论的背景                                   |
| Reasoning、普通工具调用及带 call_id 的配对输出     | 过滤；不能保证子 Agent 已拿到父方读过的文件内容                |
| 父方 Agent 角色/使用提示、旧时间提示、具体审批片段 | 按标记或匹配规则过滤，子方身份与指令按配置装配                 |
| 累计 Token 记录、实时记录、部分通信记录            | 不当作子方累计状态或通信现场继承                               |
| 压缩检查点                                         | 保留必要上下文，但清除或改写父方任务归属、局部审批证据等元数据 |
| 工具声明与上下文比较基线                           | 必须协调保留或重建，不是简单全部保留或全部删除                 |

例如父方读过 network.rs 并回答“重试可能重复提交”，子方默认可继承用户需求和这条结论，但不保证有原始读文件输出，需要时重新读取。

启用 preserve_fork_prefix 且满足基线条件时，会保留更多 ResponseItem 历史，并追加身份边界提示：前文是祖先背景，使用自己的角色、身份和任务；历史调用不意味着拥有活跃工具会话或句柄。不能把默认过滤表当作所有配置下的不变量。

## 为什么禁止用户直接给部分子 Thread 输入

2026-06-09 的 1026e9de1 明确说明：V2 ThreadSpawn 子 Agent 由父方协调，客户端直接 turn/start 或 turn/steer 会绕过协作消息路径，形成第二个冲突的工作来源。7 月 16 日编写、17 日提交的 3f0669dbd 将 TUI 中这类线程设为只读并暴露 canAcceptDirectInput；8 月 20 日 010738a25 限制设置更新；8 月 24 日 b6333bb1b 扩大直接输入检查范围。

这是 V2 ThreadSpawn 的具体策略，不能泛化到所有 Thread 或所有子 Agent 类型。上述是服务端/TUI 提交证据，不等于桌面 App 发布或灰度日期。用户可以查看不代表可以直接改变其任务；停止等保留的控制入口也不能简单概括为完全不可操作。

## Thread ID、路径与父子关系如何用于通信

- ID 输入直接解析成 ThreadId；路径输入通过 Agent 注册表解析成 ThreadId。
- 之后仍需校验目标是否是当前控制器已知的 Agent、是否有协作身份及是否符合工具限制；followup_task 不允许以根 Agent 为目标。
- 父子关系保存父 ThreadId。结果汇报可直接使用保存的 ID，不必每次先解析路径。
- 同树中可寻址成员可以直接通信，不要求消息逐级经父方转发；发消息或交付任务不改变创建时的父子关系。
- 历史来源、创建者/父方和本次任务发起者是不同概念，可以指向不同对象。

把 Thread ID 交给宿主工具读取对话，与协作工具向 Agent 投递消息是不同能力。宿主 App 可能提供额外跨对话接口，但必须核对实际工具和权限；不能仅凭名字或一次读取成功认定任意 Thread 都可收取协作任务。

## 子配置的来源与覆盖顺序

子配置以父方有效配置和调用 Step 设置为基础，依次处理请求模型/默认子模型、适用角色、服务等级、运行时审批/权限快照和工作目录。不是所有字段都遵循“最后传入的参数最大”。派发显式模型优先于默认子模型；两者都没有时保留父方当前模型。切换模型而未指定或配置子方推理强度时，采用新模型的默认推理强度。不可用模型或不支持的强度会报错。

适用角色在模型请求设置之后应用，因此角色明确设置的模型或强度可能再次覆盖，不能笼统说工具参数永远优先。普通非完整历史创建会应用角色；V2 完整历史创建在明确指定角色时也应用。最后重新对齐父 Turn 的审批策略、审批处理方式、工作目录和权限快照，因此角色不是不受约束的最后覆盖层。源码中的角色配置与任务文字“你是一名审查员”是不同输入。

工具装配应区分模型可见声明与实际执行处理器：子方以自己的有效配置走公共构建流程，具体内部工具和动态工具还受能力与开关约束，不能推断父子工具必然完全相同。
