# 验证闭环：工具能力、检查规则与模型判断

本课回答：代码修改之后，宿主应提供什么验证能力，验证程序判定什么，LLM 怎样据此修正或交付？建议难度中高；重点记住三层责任及证据范围。承接[文件变化与历史重建](0032-file-change-conflicts-and-history-recovery.md)，不构成目标工程的实施范围或验收门禁设计。

## 1. 先分清谁在做什么

贯穿任务仍是修复空输入导致的崩溃，并检查原有行为。讲解最初将运行验证、失败归因和交付判断串在一起；用户指出混合了 Agent 可提供的工具与 LLM 的判断。以下三层区分是本课的核心纠正：

| 层次 | 责任 | 不自动保证什么 |
| --- | --- | --- |
| 宿主 / Harness 与工具 | 提供执行、等待、读取输出、查看文件与差异等能力；按权限执行并回传事实 | 业务要求已满足 |
| 验证程序 | 按既定规则检查，例如编译器的类型检查、测试程序的断言 | 规则覆盖了用户全部要求 |
| LLM | 选择检查方式，结合任务理解结果、确定修正或交付 | 所有判断已被宿主确定性强制执行 |

不能把全部判断都归给模型。断言是否满足由测试程序判断；断言是否准确表达需求、覆盖是否足够，通常还需要结合任务与工程信息判断。

## 2. 通用工具与专用验证工具

宿主可以提供命令执行工具，让模型选择测试命令并读取退出状态与输出；也可以设计 `run_tests(target)` 这样的专用工具，统一调用项目测试程序并返回用例数、失败项、报告位置。后者是设计示例，不声称 Codex 当前提供这个接口。

专用工具减少命令组织和输出解析成本，类似 apply_patch 的任务操作封装。但“通过 12、失败 0”首先表达这些用例的执行结果，不自动证明全部任务完成。

当前 [ExecCommandToolOutput](../../../codex-rs/core/src/tools/context.rs) 包含原始输出、进程标识、退出码、截断策略和遗漏字节等信息，并转成工具响应供模型使用。这个结构本身没有“业务验收已通过”字段。[UnifiedExecProcess](../../../codex-rs/core/src/unified_exec/process.rs) 分别提供退出状态、退出码和超时信息；命令返回不应直接当作进程已完成。

## 3. 验证动作与验证结论

| 观察到的结果 | 当前证据 | 模型合理的后续判断 |
| --- | --- | --- |
| 进程仍在运行 | 尚无最终结论 | 继续取得结果 |
| 测试程序无法启动 | 验证没有开展 | 检查命令或环境 |
| 临时文件写入被拒绝 | 执行条件受限 | 判断权限与可行验证方式 |
| 空输入断言失败 | 有行为不符合断言的证据 | 核对实现和断言依据 |
| 相关用例完成并通过 | 被覆盖的行为通过检查 | 判断是否覆盖必要要求 |

“命令失败 → 改代码 → 重试”不是可靠的统一策略。依赖缺失或权限拒绝没有直接证明业务实现错误。反过来，命令退出码为零也可能伴随零个测试、筛选错误或部分跳过；需读取会改变结论的输出。

## 4. 选择验证就是选择要检验的主张

假设接口约定空输入返回无结果，则至少要考虑空输入行为、普通输入是否保持原有结果、调用方能否处理无结果。格式检查不能替代这些行为检查；只验证空输入也不能单独证明正常输入未受影响。

测试、编译、静态检查和人工检查各提供不同范围的证据。若工程只允许静态检查，应按静态证据交付，并说明未验证的运行行为；本课不要求为了学习编译 Codex。

当断言失败时，先依据需求判断实现与断言哪一侧有误。不能为了让测试变绿而破坏正确接口约定。测试是检验要求的手段，断言本身同样需要依据。

## 5. 验证证据绑定代码状态

版本 A 通过验证，随后修改为版本 B，不能直接宣称 B 已通过相同验证。是否重新检查取决于新变化影响了什么，不要求任何变化都重跑全部工程。说明文字修订和业务分支修订影响不同。

任务闭环可以描述为：任务要求 → 修改 → 针对当前修改的验证 → 解释结果 → 修正、处理验证阻碍或交付。这个描述中，选择与解释主要是模型决策；执行与证据回传由工具承担；具体断言判定由验证程序承担。

## 6. 模型行为要求与强制门禁

提示模型“完成前请验证”，不等于宿主建立了不可绕过的门禁。若产品确实要求指定检查成功后才允许某个交付动作，就需实现明确规则，并处理结果与代码状态的对应关系。这是额外设计选择，不是工具存在后自然具备的能力。

转型设计因此有两条线：能力建设关注工具执行范围、返回事实、错误与未完成状态；决策行为关注模型如何选择验证、解释结果并结束。前者让模型有能力取得证据，后者决定证据如何被使用。强保证应有确定性机制，不能只写成对模型的期望。

## 7. 后续连接

单 Agent 的能力与决策边界明确之后，继续讨论子 Agent 写入：独立 Thread 不自动隔离文件，分工约定不自动成为权限限制，各自验证通过也不自动证明组合结果正确。具体实现仍须按路径核对，不能提前假设 worktree、锁或自动合并存在。
