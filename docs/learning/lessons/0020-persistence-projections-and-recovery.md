# 持久化、投影与恢复：数据还在，为什么历史可能读不出来？

状态：已安排、待深入。当前先保存 Subagent 课程中插入答疑的已核对结论，不计入已完成课程；详细授课安排在第二批能力扩展课程之后。编号是文档标识，不要求按编号立即授课。

本课围绕一个问题：原始事实、查询结构和运行状态各自怎样保存，失败后由谁恢复？入门背景见[第 9 课](0009-session-lifecycle-context-and-history-projections.md#十五sqlite-为什么可以是可重建投影)。以下机制依据当前学习仓源码静态核对，本机数据是观察样本，不表示已对运行中的 App 做故障注入。

## 已讲清的主链与触发时机

rollout JSONL 保存持久历史记录，SQLite 历史投影将其中的事件解释成适合分页与查询的 Turn、Item。正常分页历史写入路径先写日志并 flush，再主动调用投影；它不是 SQLite 监听文件变化，也不等于每出现一个流式字符都更新数据库。

追加历史项、Persist、Flush 和写入器关闭都有投影机会，分页 Fork/Revert 也会处理相关日志段。投影从保存的字节偏移和序号继续读取完整记录，把查询数据与处理进度放在同一事务提交。没有新增内容就返回；尾部半行等待补全。

如果 E101 已写入日志，但数据库仍停在 E100，下一次触发可补上 E101。正常增量处理信任过去的进度，不会重新验证全部旧行。因此“进度到 E100、E50 的查询行却丢失”不会靠普通追赶自动修好。没有进度时可以从相应日志的开头建立投影；旧结果不可信时需要重建或专项修复，不能仅因进程重启就认定需要全量重建。

## 投影保存什么，空间为什么增长

历史库既保存 Turn 状态、时间和索引，也保存序列化消息项的 `item_json` 正文。它不是只存日志地址，也不是复制所有原始记录；上下文、Token 用量等原始记录不会全部原样进入普通 Turn/Item 投影。同一消息项意外重复时更新已有快照。

正文冗余换取查询便利。索引和分页控制每次读取量，不限制磁盘总量；模型上下文压缩也不等于删除完整历史。Fork/Revert 引用已有前缀以复用历史段，冷 rollout 可压缩为 `.jsonl.zst`，但日志压缩不等于 SQLite 正文压缩。

归档保留历史，不能视为删除。永久删除会检查其他历史引用，再删除对应投影和日志；有外部 Fork 引用时不能任意删除源记录。当前历史投影路径未发现固定容量淘汰旧对话的策略，历史库 `background_reclamation` 为 false；不能套用运行日志库的保留与回收策略，也不能保证删除记录后文件立即缩小。

## 异常处理：可重建不等于查询会自动修复

| 场景                      | 当前核对到的行为                                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------------------- |
| 历史数据库缺失，重新打开  | `create_if_missing(true)` 创建数据库，迁移建立表结构；不等于已经恢复内容                             |
| 表存在，但相应投影行缺失  | 普通分页查询可能返回空页，不因结果为空自动扫描日志                                                   |
| 打开、迁移或 SQL 查询失败 | 错误向上传递，分页接口可返回历史读取失败                                                             |
| 日志写入成功，投影失败    | 写入路径记录警告；日志保留，后续投影触发有机会追赶                                                   |
| 缺失进度后触发投影        | 从相应 rollout 开头建立投影，不保证一次恢复所有闲置会话和引用段                                      |
| 历史库损坏                | 配置为 `RecoveryMode::Unavailable`，未启用部分其他数据库的备份坏库后重建分支；快速检查不等于自动修复 |

普通分页查询没有通用的“查不到 → 完整重建 → 再查”流程，也没有 SQL 失败后直接读 JSONL 的透明兜底。某些其他路径会读取 rollout，但不能据此推断分页接口有同样的故障恢复能力。

重建只重新解释已有事实，不重新请求模型、运行工具或重复外部副作用。源日志及历史引用必须完整；当前 rollout 选择、父子关系等状态要逐类确认来源，不能把整个 SQLite 状态库当成可随意删除的缓存。以上未模拟运行中删除数据库、断电或文件损坏。

## 正式授课时展开的问题

1. 持久事实、查询投影、模型上下文、运行实例和控制元数据分别由谁拥有？
2. 日志 flush、SQLite 事务、WAL 与断电持久性分别保证什么？如何定位跨文件失败窗口？
3. 进度、版本、历史引用与当前路径选择如何保证可恢复性？
4. 缺失、损坏、落后和不兼容分别怎样检测；重试、修复、重建与降级的契约有什么区别？
5. 如何只读度量容量，并区分保留策略、逻辑删除、空闲页复用和物理空间回收？
6. 用隔离 fixture 验证故障场景，不操作真实用户历史；具体实验另行激活。

建议难度：高；目标深度：主链和失败语义深入。完成标准是能够独立推演“日志成功而投影失败”“空库查询”“旧行缺失但进度仍在”“Revert 后旧文件仍存在”四个场景，区分当前实现、设计需求和未验证行为。
