## 1. 一次命令的三个时刻

假设默认只允许写入 `D:\Demo`，模型请求 `python report.py`。脚本先写 `D:\Demo\report.txt`，再写 `D:\Other\report.txt`。

启动前，Harness 判断命令能否执行、是否需要审批、使用什么权限。准入不仅是危险命令识别，还涉及命令规则、审批设置与权限请求。获准执行不表示脚本内所有访问都已获准。

启动时，执行设施必须落实选定的限制。若前面判断只允许写 Demo，后面却普通启动一个不受约束的 Python，权限决定就没有接上执行。

运行中，实际访问由相应执行机制限制：Demo 写入允许，Other 写入被拒绝。第二次失败不会回滚第一次已经发生的写入。执行限制不是事后清理副作用。

```text
判断能否开始 → 确定执行权限 → 带限制执行
  → 实际访问允许或拒绝 → 结果回到原有工具调用链
```

正式接入要证明真实工具请求经过这条链，权限确实进入执行器，真实结果回到 Harness，而不只是模拟状态机有正确输出。

## 2. 补丁与 Shell 到底哪里不同

比较“用补丁修改 a.txt”与“运行 update.py 修改文件”：

| 阶段 | 补丁 | Shell（当前 exec_command 链路） |
| --- | --- | --- |
| 理解请求 | 解析明确的增删改和移动目标 | 取得命令、参数、目录及权限请求 |
| 前置判断 | 检查各目标是否可写，结合审批设置、执行约束可用性等决定 | 根据命令规则、审批设置及权限请求生成审批要求 |
| 共享编排 | 组织必要审批、选择执行限制、发起尝试 | 复用同一编排职责 |
| 实际执行 | 将补丁交给文件系统执行层，传递相应限制上下文 | 启动命令进程并落实相应限制 |

补丁目标是 `D:\Other\a.txt` 时，执行前即可看见越界。请求只是 `python update.py` 时，不能普遍列举程序运行中所有文件访问；假设命令规则允许在默认沙箱启动，越界可能在脚本真正访问 Other 时才被拦截。Shell 仍可能在启动前被拒绝或要求审批，不是所有检查都延后。

特化工具的直接操作范围更明确，不能扩大成“所有副作用和最终结果都可预见”。路径链接、运行期间状态变化、磁盘满等仍需要正确处理。

## 3. 已知目标，为什么仍需要限制

知道要改哪里，不代表有权改那里，因此前置权限判断始终必要。前置路径判断也不能普遍替代实际执行约束。

当前 `assess_patch_safety` 明确考虑补丁路径可能通过硬链接关联到允许范围外的文件，因此即使目标看起来可写，也结合沙箱可用性判断自动批准。Disabled/External 配置有明确例外，不能把“保留执行限制”说成所有配置下一律启动本机沙箱。

`prepare_apply_patch` 的自动批准结果为 `Skip { bypass_sandbox: false, ... }`：省略普通审批不等于要求绕过沙箱。实际运行时将相应沙箱上下文传给文件系统执行层。

只开放受控文件操作的其他系统，可以采用自身资源访问检查，不必与 Shell 使用相同进程沙箱；前提是覆盖所有实际访问路径并可靠处理路径语义。这个一般设计可能性不能冒充当前 Codex 已取消补丁执行限制。

## 4. 为什么共用编排，还保留具体工具

补丁需要解析与应用修改；Shell 需要启动进程、收集输出和退出状态。两者的具体操作不同，但都需要审批、执行约束选择及尝试管理。

`ToolOrchestrator` 复用公共顺序，在 `run_attempt` 中调用具体工具运行时的 `run`。它没有把补丁与 Shell 变成同一种操作，也不是所有工具必经的万能权限关卡。

各工具完全复制公共流程容易漏检查；让编排器理解所有操作细节又会使职责膨胀。当前拆分让具体工具表达请求及执行方式，共享编排组织公共流程。

## 5. 批准怎样变成本次权限

批准执行与批准扩大权限是两个问题。若申请是在默认权限下运行，批准只让操作获准开始，不能据此推导资源范围扩大。若申请明确包含额外权限，执行端才按获批内容及现有约束生成本次有效权限。

以支持按目录授权的系统为例：申请包含编号、命令、额外可写目录 `D:\Other\Reports`、授权作用域和解释原因。原因供人理解，目录清单是程序处理的结构化权限。Harness 校验路径和可申请范围，审批结果绑定原申请，不能把获批目录替换成更大范围后继续沿用批准。

批准后可近似理解为“默认权限 + 获批额外权限 → 本次有效权限”，但不可覆盖的限制必须保留，不能无条件做集合相加。执行后端将有效权限转换为相应限制配置。当前 `UnifiedExecRequest` 区分 `additional_permissions` 与 `justification`；实际提权方式依请求和配置分支而定，并非所有批准都表示按目录增权。

执行权限数据负责控制访问，审批历史负责解释和追踪，两者用途不同。一次性批准不应自动改写默认权限或让下一条独立命令继承；历史里有批准记录也不自动授予权限。“仅本次”不等于工具一返回就撤销仍运行进程的权限，具体生命周期需另行讲解。

接入应防止两种不一致：获批额外权限没有传到执行端；普通执行获批却被转换成完全放开限制。用户已表示理解这一逻辑，本课不据此宣称其掌握全部授权缓存、持久化和提权分支。

## 6. 后端把权限数据变成实际限制

有效权限起初只是 Harness 内存中的数据。普通启动一个程序不会自动让它遵守这些数据；执行接口必须同时传递命令、工作目录、文件和网络等执行约束。

后端将统一权限描述转换为平台支持的限制配置，再让操作在限制下执行。具体方式可能涉及受限执行身份、文件系统视图或平台沙箱策略，本课只定位责任，不展开系统 API。实际文件访问发生时，由相应执行机制落实限制，无需模型逐次判断。

当前 `SandboxAttempt::env_for` 把命令及权限交给 `SandboxManager.transform`；`env_for_exec_server` 为执行服务准备权限上下文，由执行端落实。不能看到本机没有包装沙箱就断定远端执行无限制，也不能仅因请求携带权限数据就断定后端已落实。

正式接入分别验证“权限算对了”和“权限落实了”。对于承诺受限执行的请求，后端不支持限制或初始化失败时应明确失败，不可静默普通启动；这是接入应守住的约束，不表示本轮已审计全部平台分支。用户已表示理解此职责边界。

## 7. 失败回传必须保留执行状态

同样是失败，命令策略拒绝、审批拒绝、启动前沙箱准备失败、运行中访问被拒绝和普通程序错误，发生时刻与恢复方向不同。前三种场景中的本次目标命令尚未执行；运行后失败则可能已有副作用，不能统一表达成“未执行”。这里不将启动准备失败扩大为任何辅助设施都没有状态变化。

假设脚本先追加日志，再生成报告，最后复制到范围外。复制被拒绝不回滚前两步；批准额外权限后整条重跑，可能重复追加日志。合理恢复是先核对报告和失败位置，再决定是否只重试复制。磁盘满等普通故障通常不能靠提权解决。

Harness 提供是否启动、退出状态、输出、拒绝信息及能够可靠观察到的变更；模型据此检查产物和决定下一步。补丁运行时在失败时仍保留此前已提交的 delta；任意脚本的所有副作用不一定都可观察，未知应保持未知。当前编排器区分沙箱拒绝与其他错误，并依据策略决定是否允许后续提权尝试，不能概括为“失败就提权重跑”，也不据此宣称所有内部重试均有完整副作用分析。
