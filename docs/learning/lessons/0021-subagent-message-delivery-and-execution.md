# Subagent 通信：收到消息，为什么不等于开始工作？

状态：Subagent 专题进行中，本节已完成分层答疑；专题整体尚未结束。本文以当前本地 MultiAgent V2 实现为范围，源码与 Git 历史已静态核对，未运行故障实验。

## 三层职责

| 层次       | 谁决定                                   | 决定什么                                                                    |
| ---------- | ---------------------------------------- | --------------------------------------------------------------------------- |
| 发送方模型 | 根据工具说明、目标状态与任务意图选择工具 | 补充信息用 send_message；需要空闲目标开始处理用 followup_task。模型可能选错 |
| 运行时     | 按明确标记、当前执行状态及唤醒策略处理   | 是否建立运行体、是否启动 Turn/Task、如何将消息交给当前执行                  |
| 接收方模型 | 获得执行机会并读到输入后                 | 如何理解内容、调用哪些工具、怎样行动与汇报                                  |

发送方选择 `send_message` 对应 `QueueOnly`，不携带启动新任务的要求；`followup_task` 对应 `TriggerTurn`，要求空闲目标开始处理。运行时不会因为正文写着“请立即执行”就自动把前者改成后者。

普通空闲目标收到 queue-only 消息后，消息可以留在信箱，此时没有模型请求，模型可能根本没有读到。目标正在工作时，消息在合适边界进入执行；任务型消息也不要求另开一个并行 Turn。两者同属 Agent 间工具，与用户在聊天框输入是不同入口；父子都可能使用工具，followup_task 不能以根 Agent 为目标。

运行体加载与启动工作是两步。冷恢复目标可能在交付前被加载，而本地已卸载的目标可保留普通消息，不必立即加载。不要用是否已在内存判断模型是否工作。

## 三个不能画等号的状态

```text
运行时收到消息 → 模型读到消息 → 模型采取行动
```

每个箭头都需要额外条件。send_message 成功不保证已经进入模型上下文；若目标一直没有后续执行，消息可能一直未被模型读到。模型读到后也不保证必然按发送者期望采取行动。

## 唤醒规则是第二层的扩展

普通空闲与等待中的工作不是同一状态。挂有 durable sleep 的线程可以由普通消息唤醒，以继续原来的工作。另有默认关闭的 `wake_on_agent_messages` 开关，允许符合条件的空闲根 Agent 因消息开始执行；它不适用于子 Agent、已中断会话和 Plan 模式。因此不能把 queue-only 概括成“任何条件下都不能唤醒”。

分层理解应先固定普通空闲目标，再学习这些附加策略，避免把配置分支误当成基本接口区别。

## 等待反馈与主动查询状态

当前 V2 的 wait_agent 等待调用方输入队列的活动，不指定某个子 Agent，也不是等待所有子任务全部完成。信箱活动、新输入和超时都可能结束等待；返回只说明等待结果，不直接代表业务验收通过。正常链路是“子任务完成 → 运行时发送结果通知 → 父运行时接收 → 父模型读取并判断”。结果通知采用 queue-only 交付，投递为尽力而为，不保证必然成功。

wait_agent 不会因为子 Agent 每读一个文件、执行一条命令而自动得到进度消息。list_agents 可主动查询名称与 AgentStatus，不依赖子模型回答；Running 是生命周期状态，不是持续心跳或进度保证。正常执行、等待模型、等待耗时命令甚至调用迟迟不返回，都可能仍显示 Running。询问进展可以发 send_message，但仍要等待目标获得读消息的机会。

“等待返回”“子任务终态”和“业务验收通过”分别由输入活动、执行状态和父模型结合任务要求判断，不能互相替代。
