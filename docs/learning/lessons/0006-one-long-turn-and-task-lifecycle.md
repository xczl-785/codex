# 第六课：一个长任务为什么仍是一个 Turn

这一课回答三个相连的问题：一个长实施任务是不是一个大 Turn；它内部怎样继续运行；Task 究竟是什么、怎样拉起和结束。

## 先给结论

正常情况下，用户提交一个长实施请求以后，从 Agent 开始处理，到最终完成、失败或被中断，整体就是一个 Turn。它可以持续很久，包含多次思考、多次模型请求、许多工具调用、文件修改、测试、上下文压缩和一条最终答复，但这些内部动作不会仅仅因为数量多而自动产生新 Turn。

Turn 的边界是“这段连续执行是否已经到达终态”，不是聊天界面显示了多少行，也不是模型被调用了多少次。

长 Turn 内部真正反复出现的细粒度单位是 Step、模型采样和工具调用。Task 则是驱动这整个 Turn 的执行程序。可以先记成：

```text
Thread：长期工作会话
└─ Session：该 Thread 当前的内存运行体
   └─ ActiveTurn：当前连续执行的边界
      └─ RunningTask：负责把这次执行跑完
         └─ run_turn 循环
            ├─ Step 1：模型采样 → 工具调用
            ├─ Step 2：带着工具结果再次采样 → 更多工具调用
            ├─ Step 3：再次采样 → 最终回复
            └─ 不再需要 follow-up → TurnComplete
```

## 一、为什么长实施过程仍然是一个 Turn

假设用户要求：阅读仓库、修改五个文件、运行静态检查、修复发现的问题、最后总结。

从用户意图看，这不是五六个相互独立的请求，而是一次连续委托。Agent 在中间调用命令、读文件和改文件，是为了完成同一份委托。只有把整个过程放在一个 Turn 中，系统才容易统一处理：

- 当前用户请求和后续 Steer；
- 一次执行采用的模型、权限、工作目录和配置；
- 本轮工具调用数、Token 用量和文件差异；
- 完成、中断、失败和总耗时；
- TUI 或 App Server 应该把哪些事件归到同一次执行中。

如果每次工具调用都算一个 Turn，会产生几个问题：

1. 用户没有发出新请求，系统却制造大量伪造的“轮次”；
2. 中断时无法表达“停止整个实施任务”，只能逐个停止某次工具调用；
3. 一条中途追加的方向调整，不知道应该交给哪一个碎片 Turn；
4. 总耗时、错误、最终回复和本轮修改难以统一归属；
5. 对话历史会被执行细节淹没，恢复和派生 Thread 也更难解释。

所以 Turn 采用用户可感知的连续执行边界，而不是内部技术动作边界。

## 二、一个 Turn 内部怎样划分

### 1. Step 不是新的 Turn

`run_turn` 会先捕获一个 `StepContext`。它代表这一步模型请求所依据的一组稳定视图，例如模型设置、工作环境和可用工具。随后核心构造模型可见历史并发起一次采样请求。

模型可能返回推理内容、助手消息或工具调用。工具调用完成后，结果会记录进历史。若模型仍需继续，下一次循环会再捕获或复用合适的 Step 上下文，并带着新工具结果重新请求模型。

因此可以把 Step 理解成：**Turn 内一次“基于当前稳定世界视图继续想和做”的执行切片。**

它存在的意义是允许长任务在运行过程中安全地接收环境、配置和工具状态的变化，同时保证一次具体模型请求内部看到的是一致的快照。如果整个长 Turn 永远固定所有状态，运行中发生的合法变化无法生效；如果状态在一次模型请求或工具调用中任意漂移，同一动作又可能前后使用不同权限或环境。

### 2. Step 与工具调用不是一一对应

不要把 Step 简化为“一次工具调用”。一次模型采样可以产生一个或多个工具调用，工具还可能并行执行。Step 更接近一次采样所使用的环境与设置快照；工具调用只是这一步可能产生的工作项。

常见过程是：

```text
模型采样 1
  └─ 返回工具调用：读取文件
       └─ 工具结果写回上下文

模型采样 2
  └─ 返回工具调用：修改文件、检查状态
       └─ 工具结果写回上下文

模型采样 3
  └─ 返回最终助手消息，不再要求继续
```

这三次采样通常仍属于同一个 Turn。

### 3. 什么让循环继续，什么让它结束

一次采样完成后，`run_turn` 会判断两类 follow-up：

- 模型是否因为工具调用等原因还需要继续；
- 活动 Turn 是否收到了待处理的新输入，例如用户在运行中发送的 Steer。

任意一项成立，循环都会继续。若上下文达到限制且仍要继续，核心可以在 Turn 中途做自动压缩，然后继续下一步；这种中途压缩也不自动产生新 Turn。

当模型不再需要继续、没有待处理输入、停止钩子也不要求追加工作时，循环才返回最后一条助手消息，Task 进入收尾。

## 三、界面为什么看起来像“思考和修改被叠起来”

界面展示方式不决定 Turn 边界。

运行期间，核心会持续发出推理增量、助手消息、命令开始与结束、工具调用、文件修改和状态变化等事件。TUI 把这些事件映射成流式内容或工作记录，并可能合并连续的命令活动、结束仍在刷新的流式区域、插入一条工作分隔线。最终答复则作为最主要的结果内容保留在视图中。

所以用户看到的近似效果是：

```text
[正在工作：思考、读取、命令、修改……]
              ↓ 完成后整理/收起
[Worked for 2m 5s]
[最终答复]
```

这里的“收起”是客户端对事件和历史单元的展示投影，不表示核心把它们切成了多个 Turn，也不表示内部只发生了一次模型请求。换一个客户端，同一批协议事件可以采用不同布局。

## 四、界面的总执行时间怎样计算

`start_task` 启动 Task 时调用 `TurnTimingState::mark_turn_started`，记录单调时钟的开始点。Task 完成或中断时，统一调用 `complete_profile_and_duration_ms`，使用当前时刻减去开始时刻，形成 `duration_ms`，再随 `TurnComplete` 或 `TurnAborted` 事件发送给客户端。

因此它主要是本 Turn 的墙钟耗时：从 Task 生命周期开始，到终态收尾时为止。它包括期间的模型等待、工具执行、压缩和框架开销，不是各次模型推理时间的简单相加，也不是 Token 数换算出的时间。

TUI 收到完成事件后优先显示服务端提供的 `duration_ms`；若没有该字段，才可能使用本地状态组件记录的经过秒数作为回退。

系统同时还记录更细的性能资料，例如：

- 第一个 Token 到达时间；
- 采样次数和重试次数；
- 采样、压缩、工具阻塞、采样间开销等阶段耗时；
- 单个命令或工具自己的耗时。

这些用于诊断一轮为什么慢，但都不改变 Turn 的身份。

## 五、Task 怎样被调度、拉起和关闭

普通用户输入走 `StartOrSteer` 决策：

1. 如果存在可接收输入的普通活动 Turn，新输入进入它的待处理队列，结果是 `Steered`，不会拉起另一个普通 Task；
2. 如果没有活动 Turn，系统创建新的 `TurnContext`，再启动 `RegularTask`；
3. Review 和 Compact Task 明确不可 Steer，避免把普通用户输入塞进职责不同的工作流。

拉起普通 Task 的主流程如下：

```text
用户输入
  → StartOrSteer 判断当前是否空闲
  → 创建 TurnContext
  → start_task(RegularTask)
  → 标记 Turn 开始、建立取消令牌和完成通知
  → 在 Tokio 后台任务中执行 SessionTask::run
  → RegularTask 发出 TurnStarted
  → RegularTask 驱动 run_turn 的多 Step 循环
```

`start_task` 会把运行信息包装成 `RunningTask`，放入 `ActiveTurn.task`。Session 在同一时刻只维护一个这样的活动 Task。若使用需要替换现有工作的 `spawn_task`，它会先以 `Replaced` 原因终止旧 Task，再启动新 Task。

正常结束时：

1. `SessionTask::run` 返回可选的最后助手消息；
2. 后台执行体刷新 rollout，确保普通事件先持久化；
3. `on_task_finished` 从 `ActiveTurn` 中取走 RunningTask；
4. 处理尚未消费的输入，计算本 Turn 的工具数、Token 和时间；
5. 发出 `TurnComplete`；发生取消时则进入 `TurnAborted`；
6. 清除活动 Turn，使 Thread 进入 idle；
7. 如果邮箱中存在能唤醒 Thread 的待处理工作，再启动下一 Turn。

中断时，Session 取走活动 Task、触发取消令牌、等待或执行 Task 的 abort 清理，并发出中断生命周期事件。它结束的是当前 Task 驱动的这一个 Turn，而不是销毁整个 Thread。

## 六、一个 Task 到底包含什么

这里要区分“Task 这个执行对象”和“本轮发生的全部内容”。Task 不是一个装满聊天历史、思考文本和文件差异的大数据包。

### Task 类型本身

`SessionTask` 是一份很小的执行契约，主要定义：

- `kind`：Regular、Review 或 Compact；
- `span_name`：运行跟踪名称；
- `run`：怎样执行该工作流；
- `abort`：中断后是否需要额外清理。

当前 `RegularTask` 本身甚至是零字段结构体。它的价值不是保存数据，而是实现“普通 Agent Turn 应怎样运行”的行为。

### 调用 Task 时传入的材料

`run` 执行时会收到：

- `Session`：访问该 Thread 的历史、服务、输入队列、工具和事件通道；
- `TurnContext`：本 Turn 锁定或解析出的模型、配置、权限、工作环境、输出约束和计时状态；
- 初始 `Vec<TurnInput>`：这次启动时要处理的输入；
- `CancellationToken`：让中断可以向深层模型或工具执行传播。

### RunningTask 保存的运行控制信息

Task 启动后，`RunningTask` 包装器保存：

- Task 的种类和具体执行对象；
- `TurnContext`；
- 取消令牌；
- Tokio 后台执行句柄；
- 完成通知；
- Agent 执行配额、诊断计数和整轮计时守卫。

### 不直接装在 Task 里的内容

- 对话历史主要属于 Session/Thread 的历史与 rollout；
- 新到的 Steer 存在活动 Turn 的输入队列和状态中；
- 工具审批、权限请求、工具调用计数等属于 `TurnState`；
- 文件修改实际发生在工作区，差异由跟踪器和事件描述；
- 最终消息是 Task 的返回值之一，也会作为事件和历史内容处理。

所以更准确的说法是：**Task 持有或获得完成本 Turn 所需的控制能力，但并不拥有这次工作涉及的一切数据。**

这种拆法让行为、长期状态、单轮配置和运行控制各自有明确归属。否则一个 Task 会变成同时保存 Thread 历史、工具系统、权限、文件状态和界面事件的巨型对象，恢复、替换、中断和测试都会变得困难。

## 七、哪些情况会产生新的 Turn

以下情况通常是新 Turn：

- 前一个 Turn 已完成，用户再发送下一条请求；
- 当前 Turn 被中断，随后重新发送或发送修改后的请求；
- 编辑旧消息通过 Fork 建立新 Thread 后，在新分支启动执行；
- Revert 截断原 Thread 历史后重新提交输入；
- 某些待处理工作在 Thread 已空闲后自动唤醒一个新 Turn；
- Subagent 在自己的 Thread/Session 中执行，它拥有自己的 Turn，而不是借用父 Agent 当前 Turn。

以下情况通常仍在原 Turn：

- 模型为了使用工具而进行下一次采样；
- 一个 Step 中执行一个或多个工具调用；
- 用户在运行中成功 Steer；
- 为继续当前工作而触发中途自动压缩；
- 停止钩子要求模型继续补充处理。

## 最后的心智模型

可以把长实施任务想成一趟列车：

- Thread 是长期存在的线路档案；
- Session 是当前投入使用的调度站；
- Turn 是一趟从发车到到站、取消或故障的行程；
- Task 是负责驾驶这趟行程的运行程序；
- Step 是途中每一段依据当前信号和线路条件做出的运行决策；
- 工具调用是途中完成的具体动作；
- UI 折叠只是把行车日志收起来，突出显示到站结果；
- 总执行时间是整趟行程的墙钟时间，而不是只计算最后一次驾驶决策。

只要“这一趟连续执行”还没有完成、中断或失败，即便内部经历很多 Step，它仍然是同一个 Turn。
