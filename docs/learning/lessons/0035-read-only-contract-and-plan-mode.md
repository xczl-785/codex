# 0035：只读运行契约与 Plan 模式

本课回答：要求 Agent 只做分析时，哪些行为由模型遵循，哪些行为由 Harness（承载模型与工具的运行系统）强制限制？Codex 的 Plan 模式在其中承担什么职责？

依据当前分支源码静态核对；没有切换当前会话模式，也没有验证各客户端的实际界面。

## 1. 先明确“只读”的对象

用户说“先分析，不要修改”，首先表达的是任务边界：此阶段应产出理解、方案和待确认事项。它不直接说明进程是否能写临时文件、测试缓存或工作区源码。

设计只读模式时，需要明确受保护资源。例如，仓库源码不可写，而工具日志与临时输出可写，是一种合理契约；它与整个进程完全不能写文件不同。测试可能产生缓存或生成文件，因此“允许测试”和“工作区不发生任何变化”不能未经核对就同时承诺。

## 2. 三层机制分别解决什么问题

| 层次 | 解决的问题 | 边界 |
| --- | --- | --- |
| 模型指令 | 告诉模型此阶段做什么、何时停止 | 模型需遵循指令；指令本身不是文件系统拒绝写入的机制 |
| 工具暴露 | 让合适操作易于调用，减少不适合的入口 | 隐藏 apply_patch 后，通用 shell 仍可能修改文件 |
| 执行权限 | 在实际访问资源时允许或拒绝操作 | 必须覆盖可达写入路径，并明确受保护资源 |

如果工具集合只有经过约束的读取接口，且所有访问均经这些接口控制，工具层也能成为有效边界。问题不在于工具层必然不可靠，而在于是否仍存在绕过该约束的可达操作。

因此，设计应让行为指令、工具集合和实际权限相互配合。用户后来要求“开始实现”，表示任务意图变化；是否同时更新执行权限，需要产品的实际机制，不能仅凭这句话推断权限已改变。

## 3. Plan 模式首先组织协作过程

当前源码中的 Plan 模板要求先探索环境，再澄清目标，最后形成足够明确、可以交给执行者实施的计划。能够从仓库发现的事实应先查证；偏好和无法自行确定的选择才需要询问。

模板禁止为落实计划而修改仓库，包括编辑源码、格式化和产生实现变更的代码生成；允许为理解任务而进行不修改受版本控制文件的探索、检查和验证。测试或构建可能产生缓存与构建产物，这也说明它的行为规则不能简单等同于“进程没有任何写权限”。

最终计划使用 `<proposed_plan>` 标记。计划是否真的足够明确、遗漏是否补齐，主要仍由模型依据任务判断；格式和流程支持不等于自动证明方案正确。

## 4. 从选择模式到具体运行行为

协议中的 `CollaborationMode` 保存模式及模型、推理强度、开发者指令等设置，并不在这个类型中定义沙箱权限。内置 Plan preset 提供 Plan 指令和推理强度设置，模型字段没有指定替换模型；客户端与配置仍可能提供自己的设置，不能把 Plan 理解成必然换模型。

上下文层根据协作模式构造对应指令，使模型知道当前阶段的工作规则。Plan 模板要求模式由开发者层的明确模式变化来切换，用户的一句实施命令本身不自动改写这一状态。

但 Plan 也不只是换一段提示词，当前源码有明确的程序分支：

- `request_user_input` 检查调用者与模式等条件，并在 Plan 模式设置阻塞式提问。该工具在其他模式的可用性还受配置影响，不能概括为永远只在 Plan 可用。
- `update_plan` 是进度清单工具，处理器在 Plan 模式直接拒绝调用。它与形成实施方案不是同一个职责。
- Turn 输入对自动续轮与 Plan 模式变化施加限制，避免自动续轮擅自改变规划状态。
- Turn 流处理识别计划内容，TUI 在满足条件时展示实施选择。

TUI 的“实施计划”操作会同时提交实施消息和 Default 模式设置；清空上下文后实施的入口则带着计划创建新的实施上下文。这里分析的是仓库里的 TUI 实现，不能直接认定当前应用界面完全相同。

## 5. 哪些是强制规则，哪些仍是模型职责

处理器拒绝 `update_plan`、提问的等待行为、客户端提交模式切换，是可在相应实现中找到的程序机制。

“不要实施”“先探索再问”“输出完整计划”是模型需要遵循的工作规则。所核对的补丁安全路径依据实际权限配置与写入路径判断，不能从 Plan 标签推导出文件系统自动只读。要承诺强制禁止写源码，还应核对真实执行权限是否覆盖所有写入路径。

这保持了三个不同的设计维度：协作模式组织当前阶段，工具提供操作能力，权限控制资源访问。它们可以组合，不必让一个模式名称同时承担所有含义；否则新增一种工作方式就可能被迫改动整套权限设计，使用者也难以判断实际保证。
