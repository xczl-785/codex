Lesson 0002 · 约 10 分钟

连续发送时：新 Turn、Steer，还是等待？

界面上的一条消息，不一定对应一个新 Turn。真正的判定依据是：当前 Thread 有没有正在运行、而且仍能接收调整的 Turn。

先给结论

空闲时发送，启动新 Turn；执行中发送，优先 Steer 当前 Turn；如果当前 Turn 已不能接收调整，输入会被拒绝、暂存或稍后重新处理。

Turn 不是聊天气泡，而是执行信封

可以把 Turn 想成一个正在处理的“执行信封”。它从核心开始处理本轮任务时打开，模型思考、工具调用、审批和继续推理都发生在里面，直到完成、中断或失败才封口。

在信封尚未封口时补一句“先别改文件，只分析”，系统可以把这句话塞进当前信封。这叫 Steer：不是重开任务，而是给正在运行的任务补充方向。

场景一：Thread 空闲

没有活动 Turn。新输入通过 turn/start 启动一轮新的执行。

场景二：Turn 正在运行

界面优先通过 turn/steer 把输入送给当前 Turn，Turn ID 不变。

场景三：状态刚好变化

界面以为 Turn 仍活跃，但核心发现它已经结束，于是刷新状态，再按新 Turn 处理。

场景四：当前不可 Steer

输入不会被悄悄吞掉；界面会保留、排队或恢复它，等待用户或下一次提交。

为什么需要 expected turn ID？

因为界面和核心是并发变化的。界面发出 Steer 请求时，原来的 Turn 可能恰好结束，新的 Turn 甚至可能已经开始。请求携带“我以为正在运行的是哪一轮”，核心就能阻止一条补充消息误入别的 Turn。

所以，“连续发送三条消息有几个 Turn？”没有固定答案

等每轮完成后再发，通常是一个 Thread、三个 Turn；在第一轮仍运行时连续补充，并且 Steer 成功，则可能仍是一个 Thread、一个 Turn。发送时机和运行状态才是决定因素。

App Server 放在哪一层？

你的“高度封装”直觉是对的，但“更高维的领域概念”不太准确。Thread 和 Turn 是系统在管理的对象；App Server 是客户端进入这些对象的统一门口。

客户端 TUI、IDE 或 SDK 表达用户意图。
App Server 校验并翻译 thread/start、turn/start、turn/steer 等请求。
核心运行时 管理 Thread、Session、Turn 和实际任务。
事件回流 把增量输出、工具状态和完成结果送回客户端。

因此更合适的比喻是：Thread/Turn 是工单和其中的一次执行，App Server 是接单台兼翻译员。它封装得很高，但它描述的是访问边界，不是更抽象的业务实体。

沿源码只看三步

  1. tui/src/app/thread_routing.rs 先看界面如何在 turn_steer 与 turn_start 之间选择。
  2. core/src/session/turn_input.rs 再看核心如何处理 StartOrSteer、StartIfIdle 和严格 Steer。
  3. tui/src/chatwidget/input_restore.rs 最后看未成功送入当前 Turn 的文字如何被保留下来。

30 秒回忆练习

模型正在调用工具时，你补充一句“先别改文件，只做静态分析”。Thread 和 Turn 一定会怎样变化？

核对答案

Thread 不变。界面会先尝试把这句话 Steer 给当前活动 Turn；成功时 Turn 也不变。只有当前 Turn 已结束或无法接收时，才会走暂存、恢复或后续新 Turn 的路径。

本课的一句话总结

Turn 的边界由执行生命周期决定，不由聊天气泡决定；App Server 负责让不同客户端以统一方式启动、调整并观察这些执行。
