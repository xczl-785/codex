# 第十六课：压缩怎样整理历史，以及哪些信息仍然可见

本课服务于实践 0003，回答压缩的输入、摘要生成和信息保留机制。它补充[第七课](0007-inline-auto-compaction.md)的生命周期解释，并为[第九课](0009-session-lifecycle-context-and-history-projections.md)的恢复投影建立基础。

## 为什么需要压缩

Agent 持续执行时，用户消息、模型输出和工具结果会增加后续模型请求的输入。模型请求容量有限，无法无限携带完整过程。可以把有效上下文理解为工作桌上的材料，把持久历史理解为档案：压缩整理工作桌，提炼继续任务所需的信息，不能据此推断档案已被删除。

以当前 Codex 本地摘要路径为例，压缩会调用模型生成交接摘要，再由 Harness 组装新的有效历史。摘要涉及选择与改写，可能丢失信息；它不能保证逐字还原原文。摘要质量应按任务目标、约束、证据、已排除方案、未决事项与副作用状态是否足够准确来判断，而不能只看缩短比例。

## 谁生成摘要，谁改变状态

`run_inline_auto_compact_task` 优先读取配置 `compact_prompt`，否则使用内置摘要指令，将其构造成 `UserInput::Text`。系统触发的指令不一定使用 system 消息角色。

`run_compact_task_inner_impl` 克隆当前有效历史，追加摘要指令，经 `for_prompt` 整理后连同基础指令调用模型。旧历史仍是消息、调用和结果等结构化条目，并非必须拼成一篇用户文章。新的一次模型请求不等于新建 Thread；自动压缩可以留在原 Turn 内。通信层的 `ModelClientSession` 也不等于 Agent 的 `Session`。

模型负责提炼；Harness 负责触发、组织输入、接收结果、组装新历史、替换状态并记录检查点。当前本地实现会组合按规则保留的用户材料和摘要，并在相应路径补入初始上下文。压缩自身也可能超过容量，本地路径对此有删除较早历史项后重试的处理。

## 输入不是所有历史事实的完整副本

压缩使用当前有效历史，而不是自动重新读取从 Thread 开始保存的全部原始记录。此前已经压缩时，下一次处理的可能是前次摘要、保留材料及之后的新历史。

| 内容 | 能否被使用的边界 |
| --- | --- |
| 消息与工具调用 | 必须仍在有效历史并进入请求 |
| 工具结果 | 可能在返回或记录时已经截断 |
| reasoning | 取决于协议返回并保留的摘要、可选内容或加密条目，不能视为完整内部思维日志 |
| 失败 | 模型历史里的错误可被使用，内部日志与未暴露重试不保证包含 |
| 文件修改 | 补丁、调用参数、读取结果或 diff 可提供证据，不自动包含磁盘当前完整状态 |

发送前还会整理调用与结果配对，处理孤立结果和不支持的媒体。因此，请求不等于原始持久日志的逐字复制。远端压缩另有专门接口，部分路径还会在发送前裁剪工具结果；本地摘要实现不能代表所有服务端细节。

## 定制交接信息

摘要指令可以要求保留当前工作阶段、用户指定的推进方式、最近改变方向的要求、未回答问题和被暂缓事项。以教学为例，应写清“用户要求暂缓练习，先连续追问机制”，而不是只写“正在学习压缩”。还应区分已讲解与已验证掌握、用户明确要求与助手推断。

稳定协作规则适合持续生效的指令；当前推进位置适合摘要。提示词只能引导提炼，不能保证完全无遗漏。源码模板通过 `include_str!` 嵌入，编辑它不等于运行时热更新；配置层提供 `compact_prompt` 与 `experimental_compact_prompt_file`，但必须确认运行路径实际使用它们。本轮没有修改压缩配置或源码。

## 已完成的场景推理

假设完整报错堆栈保存在持久历史，压缩后的有效历史只剩“导出失败与路径编码有关”。用户要求第三行原文，当前摘要不足以可靠作答。若场景明确提供历史读取工具，Agent 应定位并读取原文，再回答；不能把这项场景约定当成所有 Codex 环境必备能力。

找回原文不证明摘要无损：这是借助外部保存的原文补充信息。即使每次都检索，也不能仅凭摘要还原原文。检索结果进入有效历史后，若再次压缩又未保留它，模型仍不能可靠逐字复述。当前能否回答取决于本次请求实际包含什么；能否重新找回取决于工具范围、查询机制、原文是否存在以及调用是否成功。

下一问题是：压缩记录为什么保存 replacement history，新 Session 怎样据此重建有效历史？该问题进入恢复专题，不能因本课讲解完成而认定恢复边界已经掌握。

## 后续复盘：检查点与恢复决策

在持久化成功、没有历史回退的简单场景中，若记录是“旧历史 A → 检查点 H₁ → 新历史 B → 检查点 H₂ → 新历史 C”，恢复应以 H₂ 为基线，按原顺序接上 C。它不是先 C 后 H₂，也不是原始日志的一个连续可见区间。`session/rollout_reconstruction.rs` 中的 `reconstruct_history_from_rollout` 从较新记录向前确定仍然有效的替换历史和必要元信息，再处理其后的记录。实际实现还考虑回退与旧格式，不能把简单场景当作全部分支。

重放记录是重建历史，不是再次执行历史中的工具。检查点也不保存旧进程的完整内存、Future、文件句柄或网络连接。新 Session 知道之前在做什么，不等于恢复旧执行现场。

普通 FunctionCall 缺少结果时，`context_manager/normalize.rs` 的 `ensure_call_outputs_present` 会在调用之后补入使用相同 call_id、文本为 `aborted` 的合成 FunctionCallOutput。该处理位于模型输入历史整理路径；不能单凭这个函数推断已回写持久历史。`history_tests.rs` 的 `normalize_adds_missing_output_for_function_call` 验证了该配对行为。

这个标记不是外部执行证据。追加文件可能尚未开始、只写了一部分，或已完成但结果尚未保存。补齐调用结构不能证明没有副作用，也不授权自动重跑。合理的恢复策略是通过新调用核验当前状态，再决定完成、修复或重试。

教学例子为每条报告增加唯一 record_id：完整记录已存在就不重复追加；确认不存在且没有残留或仍在进行的写入时才考虑执行；部分写入先处理不完整状态。唯一编号本身不保证幂等，工具还需实现相应去重与并发控制。协议 call_id 用于调用与结果配对，不自动提供业务幂等性。新的核验结果证明当前状态，不等于找回旧调用丢失的返回值。

只读操作通常没有重复写入的风险，但重新读取的内容可能变化。任务要当前状态时可重新观察；任务要第一次的原文时，需要当时的结果、版本或快照。恢复应分别判断重新执行的副作用与新结果是否满足任务，而不把“可安全重读”误认为“两次观察必然相同”。用户已在场景中明确指出文件可能被外部修改。

## 容量判断、继续信号与失败出口

工具结果长度限制与累计上下文容量是两层控制。即使单次输出有界，连续调用仍可累积到阈值。`session/turn.rs` 的 `run_turn` 在一次采样及工具处理后收集继续信号与容量状态，主要判断为 `needs_follow_up && (requested_new_context_window || token_limit_reached)`。无需继续时，这个中途分支不一定立即压缩；轮前还有单独检查。

`needs_follow_up` 表示需要后续模型请求，不是任务质量验收。`stream_events_utils.rs` 的 `handle_output_item_done` 在识别到工具调用、或需反馈给模型的错误时设置该标记；响应处理累积各条目的标记，明确的 `end_turn = false` 也要求继续。外层再与 `has_pending_input` 合并。工具失败仍可能需要模型读取反馈，模型只给出最终文本也不证明所有用户要求都已满足。结束 hooks 等还有另外的控制逻辑。

`session/context_window.rs` 根据活动上下文、自动压缩计数范围、配置阈值及可用窗口计算状态。自动压缩阈值不等于 Provider 的实际硬上限，提前整理不保证永远不超限。当前轮前检查发生在新用户消息和上下文更新记录之前，源码 TODO 明确提出应提前估算待加入内容，不能将该检查描述成精确验证最终完整请求。

压缩内部与外层失败应分开。本地摘要路径对一般错误按次数重试，对摘要请求自身超限尝试移除较早历史项；远端部分路径发送前裁剪输出，特定条件下才有模型上下文 fallback。不能把这些分支推广成统一、必然成功的恢复方案。

中途压缩成功后安装历史并在同 Turn 内继续；最终失败后一般报告错误并退出当前 run_turn 路径，中止类错误向上传递，不直接沿成功分支继续普通采样。轮前压缩失败同样会退出；用户再次发送“继续”不代表绕过容量检查。普通采样收到 `ContextWindowExceeded` 时标记用量已满并返回错误，不把它当普通网络波动无限重试。这些措施提供失败出口，不能保证任意历史自动恢复可用。

若文件修改已经成功，随后压缩失败，文件变化不会自动回滚。用户已正确判断这两项结果独立，后续应先核对已完成事实与当前文件状态，而不是重复修改。
