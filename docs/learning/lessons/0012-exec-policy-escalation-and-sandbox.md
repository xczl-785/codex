# ExecPolicy、权限提升与沙箱到底怎样配合

本课继续沿 `exec_command` 的安全执行链，回答三个容易混在一起的问题：

1. ExecPolicy 怎样知道一条命令应该允许、询问还是禁止；
2. 模型怎样知道当前命令可能需要申请额外权限；
3. “先在沙箱中运行”到底是不是一次模拟或预演。

最重要的结论是：

> ExecPolicy 判断命令应当怎样处置，模型可以提出权限申请，而沙箱负责在真实执行时强制限制进程。沙箱执行不是预演；执行成功后不会在所谓“真实环境”中再运行一遍。

## 1. 先把几个职责重新摆正

一次命令执行涉及几种不同问题：

| 机制 | 回答的问题 |
| --- | --- |
| `PermissionProfile` | 当前环境默认允许访问哪些文件、目录和网络资源 |
| `ExecPolicy` | 这条具体命令应当 `Allow`、`Prompt` 还是 `Forbidden` |
| `ApprovalPolicy` | 遇到需要额外授权的情况时，是否允许发起审批 |
| `Approval` | 用户或审查者是否同意这一次具体请求 |
| Sandbox | 进程真正运行时，怎样从系统层面限制它的资源访问 |

它们不是四次重复审批，而是从不同角度拆开控制：

```text
权限范围：默认能做什么
命令策略：这次想做什么
审批机制：例外情况能不能询问
沙箱执行：进程实际上不能越过哪里
```

### 1.1 先区分资源范围与命令规则

`PermissionProfile` 可以借 Linux 文件权限理解：它规定对资源能做什么。但它不是文件本身的 `755/777`，不会直接把目录改成这些权限，也不能让普通进程突破系统账户已有权限。它描述 Agent 执行环境的资源边界，由平台沙箱落实。

假设默认范围为：`D:\Project` 可读写，`D:\Archive` 只读。Profile 回答“能不能写 Archive”；ExecPolicy 回答“这条命令能不能执行、要不要审批”。

例如，可以另行配置 `git status → Allow`、`git reset --hard → Prompt`。这是教学规则示例，不是默认配置承诺。两条命令都在 Project 中执行，资源范围相同，但后者可能丢弃修改，需要命令层面的控制。仅有目录读写权限表达不了这种区别。

`Allow` 应先理解为通过命令规则这一关，不能单凭这个枚举推断最终沙箱模式。显式规则、本次权限请求、审批与环境约束仍会影响执行方式；不要把所有 Allow 一概解释为“必定留在默认沙箱”。

### 1.2 自定义脚本的副作用怎样受到限制

执行 `python generate_report.py` 时，Codex 不必提前读懂脚本或预测全部路径。即使目标由用户输入或字符串拼接决定，Python 真正创建、打开文件时，也必须向操作系统提出具体的资源访问请求。

```text
Profile 规定 Archive 只读
  → 平台适配代码转换为可执行的沙箱限制
  → Python 在限制下运行，计算出目标路径
  → 请求以写入方式打开目标文件
      Project/report.txt：权限允许时成功
      Archive/report.txt：被访问控制拒绝
```

系统检查真实访问目标，不是仅看启动目录，也不依赖自定义命令的名字。文件访问失败可能先表现为 Python 的 PermissionError；工具层如何归类为沙箱拒绝还需结合执行证据，不能把所有 PermissionError 都当作 Codex 沙箱问题。

沙箱负责资源边界，不理解全部业务意图：覆盖 Project 中的重要文件可能仍符合可写权限。因此命令检查与资源隔离都有价值。

Windows 当前源码入口为 `codex-rs/windows-sandbox-rs/src/resolved_permissions.rs` 中的 `try_from_permission_profile`、`try_from_permission_profile_for_workspace_roots` 和 `writable_roots_for_cwd`；它们提取运行时文件/网络规则并解析目录范围。平台启动适配入口为 `codex-rs/sandboxing/src/manager.rs`。这里说明职责，不要求学习者手写系统隔离设施。

## 2. ExecPolicy 不是“禁止命令枚举表”

ExecPolicy 的最终决定确实是一个枚举：

```rust
enum Decision {
    Allow,
    Prompt,
    Forbidden,
}
```

但 Codex 没有枚举世界上所有危险命令。这样的清单无法维护，因为同一个程序的不同参数可能有完全不同的风险，命令还可能经过 shell、管道、子命令或脚本包装。

ExecPolicy 主要组合了三种来源：

```text
可配置的前缀规则
    +
内置危险行为识别
    +
没有匹配时的默认策略
```

### 2.1 可配置的前缀规则

Codex 会从配置层对应的 `rules/*.rules` 文件加载策略。规则使用受控的 Starlark 风格语法，例如：

```python
prefix_rule(
    pattern = ["git", "status"],
    decision = "allow",
)

prefix_rule(
    pattern = ["git", "push"],
    decision = "prompt",
    justification = "Pushing changes modifies the remote repository.",
)

prefix_rule(
    pattern = ["some-dangerous-tool", "delete"],
    decision = "forbidden",
    justification = "This operation is prohibited by policy.",
)
```

匹配对象不是一整段模糊字符串，而是解析后的参数序列：

```text
git status --short
    ↓
["git", "status", "--short"]
```

因此规则 `['git', 'status']` 可以匹配 `git status`、`git status --short` 等命令，但不会匹配 `git push`。

### 2.2 组合命令会被拆成多个片段

对于：

```bash
git status && npm publish
```

Codex 会尽可能拆成：

```text
git status
npm publish
```

再分别检查。多个结果会取更严格的一个：

```text
Allow < Prompt < Forbidden
```

所以：

```text
Allow + Prompt    → Prompt
Allow + Forbidden → Forbidden
Prompt + Forbidden → Forbidden
```

这避免了在一串命令前面放一个安全命令，就让后面的危险命令搭便车。

### 2.3 内置危险行为识别

如果没有显式规则匹配，Codex 还会使用危险命令启发式判断。它会考虑命令参数、shell 包装、PowerShell 解析和多个命令片段，而不只是看程序名称。

被识别为危险并不一定立刻等于 `Forbidden`：

```text
危险行为 + 当前允许询问 → Prompt
危险行为 + ApprovalPolicy=Never → Forbidden
```

因此，“行为看起来危险”和“最终禁止执行”是两个阶段。

### 2.4 没有规则匹配时仍有默认策略

在 `OnRequest + 受限沙箱` 下，一条没有被识别为危险、也没有申请提权的普通命令通常可以直接尝试：

```text
未知但不明显危险的命令
    ↓
无需先询问
    ↓
留在沙箱中执行
```

这里的 `Allow` 只表示“不需要进一步审批”，不表示获得完整系统权限。

### 2.5 强制要求只能收紧

`requirements.toml` 里的托管执行规则可以配置 `Prompt` 或 `Forbidden`，但不能配置 `Allow`。它表达的是管理方的硬约束，只能把操作收紧，不能借约束层授予更大信任。

## 3. 模型怎样知道可以申请权限

模型不是只靠一次失败“猜出”还有提权功能。Codex 会给模型三类直接信息。

### 3.1 当前权限说明

Codex 根据有效的 `PermissionProfile` 和 `ApprovalPolicy` 生成开发者指令，告诉模型当前工作区的读写范围、网络状态和审批模式。

模型因此可能在执行前就判断：

```text
写仓库内文件 → 默认权限可能足够
写工作区外目录 → 默认权限很可能不足
下载依赖 → 当前网络策略可能阻止
```

### 3.2 工具 Schema

`exec_command` 的工具定义会向模型说明参数，例如：

```text
use_default
  使用当前默认沙箱

with_additional_permissions
  保留沙箱，只为本次命令增加明确的文件或网络权限

require_escalated
  申请在默认沙箱之外执行
```

工具定义还会说明 `justification` 是展示给用户的审批问题。因此模型不仅知道参数名称，也知道合法值和用途。

### 3.3 OnRequest 专用权限指令

在 `OnRequest` 模式下，模型会明确收到这样的规则：重要命令如果明确因沙箱失败，或很可能因为沙箱网络限制失败，可以使用 `require_escalated` 和 `justification` 重新调用。

相反，在 `Never` 模式下，指令会明确告诉模型不要提供权限提升参数，因为请求会被拒绝。

所以 `OnRequest` 的完整含义是：

> 当 Agent 在工具调用中明确请求扩大权限时，系统才进入相应的审批流程。

这里的 Request 是 Agent 的工具调用请求，不是用户必须再发送一条聊天消息。

## 4. 模型是否必须先失败一次

不一定。

如果任务显然需要写工作区之外、启动 GUI 或执行其他超出当前范围的动作，模型可以在第一次调用时就申请相应权限。

如果无法预先确定，例如 `cargo test` 是否需要工作区外缓存，模型可以先使用默认权限。失败后再根据返回结果分类：

```text
编译错误 → 修代码
测试失败 → 查测试逻辑
路径错误 → 修路径
SandboxDenied → 考虑申请额外权限
依赖下载或 DNS 错误 → 判断是否可能是网络限制
```

所以不是“任何失败都提权”，而是“失败结果为判断是否提权提供证据”。

## 5. 沙箱到底是什么

### 5.1 沙箱是受限的真实执行，不是模拟器

在本课程语境里，沙箱可以先理解为：

> Codex 启动了一个真实操作系统进程，但只给这个进程一组受限的文件系统、网络和环境能力。

最容易误解的地方是把沙箱想成：

```text
复制一份仓库
在副本里预演命令
成功后再去真实仓库执行一次
```

Codex 的普通命令沙箱不是这种机制。

更接近真实情况的是：

```text
真实工作区
    ↓
启动一个受限制的真实进程
    ↓
进程直接读取或修改允许范围内的真实文件
    ↓
越界访问由沙箱阻止
```

因此，在 workspace-write 沙箱中执行：

```powershell
Set-Content .\result.txt "done"
```

如果当前仓库是可写范围，`result.txt` 会真实出现在仓库里。它不是临时副本，也不会等第二次执行才生效。

### 5.2 “先在沙箱中运行”是什么意思

这句话真正表示：

```text
第一次真实执行时，就带着默认安全边界启动进程
```

而不是：

```text
第一次模拟
第二次正式执行
```

典型过程是：

```text
命令
    ↓
带默认 PermissionProfile 启动受限进程
    ↓
允许的读写真实发生
    ↓
不允许的访问被拒绝
```

### 5.3 沙箱执行成功后不会再运行一次

如果命令在沙箱里成功：

```text
沙箱执行成功
    ↓
收集 stdout、stderr、退出码和耗时
    ↓
把结果返回给模型
    ↓
结束
```

不会接着做：

```text
再到“真实环境”执行同一命令
```

因为沙箱里那一次本来就是在真实环境中执行，只是权限受限。

## 6. 在沙箱中运行会产生什么后果

沙箱主要限制进程能接触的资源，而不是修改程序本身的业务逻辑。

### 6.1 允许范围内的副作用是真实的

如果工作区可写，那么命令可以真实地：

- 创建和修改仓库文件；
- 生成构建产物；
- 修改 Git 工作树；
- 在允许目录中创建缓存或临时文件。

这些变化不会因为进程处于沙箱就自动回滚。

### 6.2 越界访问会失败

如果某个目录不在可写范围内，程序尝试写入时可能收到：

```text
Permission denied
Access is denied
Operation not permitted
Command denied by sandbox
```

网络受限时，也可能表现为连接被拒绝、域名解析失败或依赖下载失败。

### 6.3 子进程通常也受边界约束

命令启动的编译器、脚本或其他子进程不能因为是“孙进程”就自然逃出限制。沙箱执行机制的目标就是让进程树继续受到相应边界约束。

### 6.4 沙箱不是事务和自动回滚

假设命令依次执行：

```text
1. 修改仓库内 A 文件       → 允许，已经生效
2. 创建仓库内 B 文件       → 允许，已经生效
3. 尝试写工作区外 C 文件   → 被沙箱拒绝
4. 命令失败退出
```

沙箱通常不会自动撤销前两步。因此：

> 沙箱限制访问范围，但不保证命令具有事务性，也不保证失败时恢复原状。

这也是为什么危险命令不能只依赖“先运行看看”。ExecPolicy 和审批仍然需要在启动前判断明显危险的行为。

## 7. 什么情况下可能执行第二次

只有第一次受限执行失败，而且策略允许扩大权限后重试时，才可能出现第二次执行。

概念上有两种形式。

### 7.1 Agent 发起第二次工具调用

在 `OnRequest` 下常见的是：

```text
第一次 exec_command：use_default
    ↓
沙箱拒绝，结果返回模型
    ↓
模型确认是权限问题
    ↓
第二次 exec_command：require_escalated
    ↓
审批通过后再次执行
```

这是两次明确的工具调用。

### 7.2 执行编排器进行提升重试

在其他允许的审批模式或特定网络审批路径中，执行编排器也可能在沙箱拒绝后发起审批，并在批准后进行无沙箱或扩大权限的重试。

无论是哪种形式，都要注意：第一次执行可能已经在允许范围内产生部分副作用。第二次执行不是“把第一次正式落地”，而是重新执行命令。

所以对于不可重复执行的操作，必须格外谨慎。例如发布、转账、发送消息或创建外部资源，不能随意采用失败后整条重跑的思路。

## 8. 提权后仍然失败意味着什么

`require_escalated` 只是请求绕过 Codex 的默认沙箱，不等于自动获得 Windows 管理员或 Unix root 权限。

审批通过后仍可能因为以下原因失败：

- 程序自身错误；
- 操作系统账户没有管理员权限；
- 企业或托管策略不可覆盖；
- 必须保留的 denied-read 规则阻止完全绕过沙箱；
- 远程执行器不支持所请求能力；
- 网络或外部服务真的不可用。

这时模型应根据失败类型换方案或报告阻塞，而不是不断重复相同的提升请求。

## 9. 一条完整执行链

```text
模型阅读当前权限说明和 exec_command Schema
    ↓
生成命令及本次 sandbox_permissions 请求
    ↓
ExecPolicy 拆分并检查命令片段
    ├── Forbidden → 拒绝
    ├── Prompt → 检查是否允许审批并等待决定
    └── Allow → 继续
    ↓
根据 PermissionProfile 选择实际沙箱参数
    ↓
在真实工作区启动受限的真实进程
    ├── 成功 → 返回结果，不再重复执行
    └── 被沙箱拒绝
           ↓
       返回模型，或在策略允许时审批后重试
```

## 10. 批准如何变成权限，批准能保留多久

ApprovalPolicy 是请示制度，Approval 是具体答复，reviewer 决定由用户还是自动审查器回答。允许申请不等于已经获批；Auto-review 更换审批者，不自动扩大默认 Profile。

审批请求携带命令、目标、所需权限和理由。执行器依据请求与批准决定安排执行：明确追加权限时，为本次执行组合默认 Profile 与获批权限，保留其他沙箱限制；require_escalated 则申请绕过默认沙箱，仍受不可覆盖的环境约束。理由文字不是系统级路径限制，不能把“为了写一个文件”当成进程实际仅能写该文件。

授权复用范围与执行资源范围是两个维度：

| 方式 | 保存与复用 |
| --- | --- |
| Approved / 本次批准 | 放行当前请求，不建立未来匹配规则 |
| ApprovedForSession | 会话缓存按工具定义的键匹配，不能理解为所有命令免审 |
| ApprovedExecpolicyAmendment | 保存命令前缀规则，未来匹配命令按规则处理 |
| 修改权限配置 | 改变之后使用的默认资源范围，与保存命令规则不同 |

一次批准不会因 exec_command 达到 yield 返回就让仍存活的进程立即丧失执行权限。审批复用期结束或规则删除，也不等于已有进程自动终止或已有副作用回滚。

源码入口：`protocol/src/protocol.rs` 的 ReviewDecision、`core/src/tools/sandboxing.rs` 的 ApprovalStore/with_cached_approval、`execpolicy/src/amend.rs` 的规则持久化。不同审批种类、工具与界面提供的选项可能不同。

## 11. 失败案例与边界

报告脚本先追加工作区 runs.log，再生成工作区 report.txt，最后复制到只读 Archive。若前两步成功而最后被拦截，日志和源报告保留。失败返回后先核对报告完整性、正确性与是否属于本次任务，确认可用再只申请复制，避免重复追加日志或覆盖报告。

若复制权限已经生效但磁盘已满，应归类为环境容量导致的执行失败，继续提权无益。重试前检查可用空间和目标残留，确认替换授权，成功后核对源目标内容或哈希；仅文件存在、能打开不足以证明完整复制。

| 拒绝位置 | 本次执行进程 | 先前副作用 |
| --- | --- | --- |
| 命令明确 Forbidden | 不启动 | 不撤销更早操作 |
| 审批 Denied | 待批准命令不启动 | 不撤销更早操作 |
| 运行时 SandboxDenied | 本案例中已经启动 | 允许范围内修改仍保留 |

SandboxDenied 是拒绝类别，不表示内部审批已经失败，也不标识结果是否已经交回模型。普通 exec_command 的 OnRequest 文件越界路径通常将失败返回模型，再由模型明确申请；其他策略、工具覆盖或特定网络分支可在调用内重试。内部重试可复用 CallId，但创建新 Attempt；模型再次调用则是新 Tool Call。完整链路以 `core/src/tools/orchestrator.rs` 与对应 runtime 的判断为准。

模型可能只知道部分规则。即使它不知道有效 Exec Policy 的禁止项而提交提权请求，执行器仍先检查规则，命中 Forbidden 后拒绝，不因提权参数进入正常审批放行。规则匹配不能看穿任意脚本，资源沙箱仍有独立价值。

若保留沙箱仅批准本次 Archive 写权限，脚本随后写 Other 仍会被拦截；批准运行脚本不等于批准脚本任意副作用。

## 12. 本课的记忆锚点

1. ExecPolicy 枚举的是决定，不是世界上所有危险命令。
2. 命令判断来自前缀规则、危险行为识别和默认兜底策略。
3. 模型通过权限指令、工具 Schema 和执行结果知道如何申请权限。
4. `require_escalated` 是权限申请，不是模型自己授予权限。
5. 沙箱是带限制的真实执行，不是预演副本。
6. 沙箱内允许的文件修改会真实生效，也不会自动回滚。
7. 沙箱执行成功后不会再执行一次；只有失败并获准提升时才可能重试。
