# 怎样设计并验证一个有用的 Skill

本课从运行机制回到编写决策：Skill 应改善任务中的具体判断，不能只把通用建议包装成长文。前置的发现、选择和上下文机制见课程 0025—0028。编写原则参考当前仓库的 [skill-creator 资料](../../../codex-rs/skills/src/assets/samples/skill-creator/SKILL.md)；本文是课程，不是在安装或修改真实 Skill。

## 1. 从预期行为变化开始

以 recovery-analysis 为例，目标是分析程序崩溃后的恢复正确性。若正文只有“仔细阅读、全面分析、准确回答”，很难改善模型原有行为。有效的内容应引导它区分持久事实与内存投影，定位写入边界，检查重放是否重复外部副作用，以及部分写入如何处理。

因此先问：没有这个 Skill 时容易遗漏什么？加载后，哪些判断或操作应发生变化？不要先建一套目录，再寻找填充内容。

## 2. description 帮助选对，正文帮助用对

“分析代码并解决问题”几乎适用于所有任务，会吸引无关请求。更精确的描述可以是：

```yaml
name: recovery-analysis
description: >
  分析持久化、崩溃恢复与事件重放的正确性。
  用于判断状态丢失、重复执行、部分写入及恢复顺序问题。
```

适用条件必须能在选择阶段取得。若只有读完正文才知道什么时候该用，选择机制缺少依据。描述也不应罗列所有沾边能力；排除条件只用于阻止可能的误选。

## 3. 共同方法留在正文，分支知识按需读取

```text
recovery-analysis/
  SKILL.md
  references/sqlite-recovery.md
  references/file-log-recovery.md
```

正文先要求定位持久状态、写入边界及恢复入口，所有场景都区分持久事实、可重建状态和不可安全重复的副作用。然后依据实际存储方式读取 SQLite 或文件日志资料，沿一个具体崩溃位置推演恢复结果并记录源码证据。

正文保存共同方法、关键约束和分支路由；reference 保存分支详细规则。不能为了减少字数把关键要求藏到不一定读取的文件里。单一且短小的 Skill 不需要人为拆分。

## 4. 脚本处理可重复的机械工作

解析日志、检查序号缺口和重复项、报告异常位置等，输入输出明确，适合脚本。判断恢复机制是否正确仍需结合事务边界和重放语义。序号连续不能单独证明恢复正确。

脚本应说明输入、输出、调用方法和失败表现。解析失败应报告失败，不能用空结果伪装“没有异常”。Agent 根据脚本给出的事实作解释；脚本仍受实际工具权限、环境和依赖约束。

## 5. 固定关键条件，保留合理操作空间

“未定位持久化完成边界，不得断言崩溃一定不丢失”“区分静态推断、测试和运行观察”保护结论正确性，应该明确。固定先打开 A 再打开 B 的顺序则可能不适用于不同工程；可改为先定位写入与恢复入口，再沿调用关系确认状态变化。

约束强度应对应偏离的具体后果。Skill 不自动扩大用户任务，也不因为流程中写了外部动作就获得执行授权。

## 6. 验证选择与执行效果

格式检查只能证明文件基本可解析。至少检查适用、误选和失败场景：

| 输入或条件 | 应观察的行为 |
| --- | --- |
| 崩溃后任务重复执行 | 分析重放与副作用，而不只检查文件保存 |
| 修改按钮颜色 | 不因涉及代码就使用恢复分析 |
| SQLite 恢复问题 | 按需读取 SQLite 资料，不无故加载全部分支 |
| 恢复入口未找到 | 说明证据缺口，不编造机制 |
| 检查脚本失败 | 报告失败，不当作无异常结果 |

比较使用前后的决策质量及证据完整性。输出更长、步骤更多不是有效性的充分证据。本课列的是待验证场景，未实际运行 Skill 评测。

## 7. AGENTS.md、Skill 与宿主代码的分工

| 载体 | 主要问题 | 例子 |
| --- | --- | --- |
| AGENTS.md | 在这个项目或目录工作应遵守什么约定 | 验证命令、生成文件约定、文档位置 |
| Skill | 做这一类任务应采用什么方法 | 恢复分析、迁移验证、文档编写 |
| 工具与宿主代码 | 哪些条件必须由程序检查、执行或阻止 | 路径授权、参数校验、并发上限、取消及幂等 |

AGENTS.md 与 Skill 都向模型提供指令，不能代替运行时强制机制。写下“不得修改某文件”不会自动使文件系统只读。对必须保障的边界，模型提出操作后仍需经过实际检查；[工具编排器](../../../codex-rs/core/src/tools/orchestrator.rs)使用环境权限和审批策略组织执行。

也不能把“跨项目”作为 Skill 的必要条件。项目专用但仅迁移任务需要的完整流程，可以放在项目 Skill；AGENTS.md 指明迁移时使用它。前者说明方法，后者说明本地适用约定，避免两处复制完整流程。

同一个需求可以分层实现。例如 AGENTS.md 记录本项目的验证命令，Skill 指导选择验证范围，工具返回真实结果，CI 在项目明确要求时阻止失败变更进入发布。这是不同职责，不是让多份提示词互相覆盖。

## 8. 多 Skill 组合要有职责和交付关系

recovery-analysis 产生有证据的分析结论，agent-docs 将结论写成文档，是自然的先后组合。每个 Skill 说明自己解决什么问题、需要什么输入、交付什么结果，避免都声称接管完整任务或强制相互冲突的输出格式。

正文都进入上下文，不代表宿主已经解决流程冲突。应按用户要求、适用范围及指令优先关系处理，不能默认最后加载者获胜。只有冲突会实质改变结果且现有上下文无法判断时才澄清。

载体选择可用三个问题判断：换任务但仍在本项目是否需要？换项目但仍做同类任务是否可复用？模型即使漏看或误解是否也必须守住？分别帮助定位项目指令、Skill 方法与程序保障。

下一步完成接入设计讨论，再整体回顾 Skills 专题并衔接实践。Skills 接入不自动包含 CodebaseAgent 的写入、权限或沙盒能力升级。
