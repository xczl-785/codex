# Subagent 停止工作之后：中断、回收、关闭与归档

状态：本节已讲并收束。目标是判断“Agent 不再执行”究竟改变了任务、内存运行体还是协作与存储状态。依据当前分支静态阅读，不代表已做运行故障实验。

## 先看一个连续场景

A 派 B 调研数据库恢复模块。查错版本时，A 希望停掉当前调查再指定正确版本；B 完成后暂时没任务，系统希望释放资源；项目结束后，用户想归档对话。这三个需求都会出现“停止工作”，却有不同对象和后续安排。

| 操作             | 目的             | 保留与变化                                        | 后续                           |
| ---------------- | ---------------- | ------------------------------------------------- | ------------------------------ |
| interrupt_agent  | 调整当前任务     | 请求停止当前执行，保留协作身份与历史              | 可用 followup_task 交付新任务  |
| 空闲回收         | 降低驻留资源占用 | 卸载运行体，保留身份、必要环境和待处理邮箱        | 有执行需求时重新加载           |
| close_agent 路径 | 结束协作者的使用 | 记录 Closed，并关闭相关活跃运行体、释放登记和邮箱 | 不能视作普通空闲恢复           |
| thread/archive   | 管理对话归档     | 处理运行体并写入归档状态                          | 归档状态与运行状态仍是不同维度 |

当前对话工具面只暴露 interrupt_agent，没有 close_agent；后者是仓库实现中的路径，不保证当前模型能够调用。归档依据 App-server 实现，不猜测其他客户端额外行为。

## 中断停止的是当前任务

A 发现 B 查错分支，可以先调用 interrupt_agent，再通过 followup_task 说明正确任务。中断本身没有携带新的工作目标，也不撤销已写文件或已发出的外部请求。外部工具取消与进程的命运仍需遵循[课程 0017](0017-cancellation-and-process-lifetimes.md)中的执行契约。

V2 工具返回 previous_status，即派发中断前观察到的状态；返回 Running 不代表中断失败。后端提交 Op::Interrupt，这个返回不能当作所有取消清理已完成的证明。目标已卸载或运行体已死时不会为了中断重新加载；根目标与自我中断受限制。

入口：[中断规则](../../../codex-rs/core/src/agent/control/interrupt.rs)、[工具返回](../../../codex-rs/core/src/tools/handlers/multi_agents_v2/interrupt_agent.rs)。

## 空闲回收保留未来协作的可能

B 完成第一轮后，A 可能很久才补派工作。让所有已完成 Agent 长期占内存没有必要；卸载可以释放运行资源，同时保留“这还是那个 B”的身份。

当前 V2 回收不仅检查状态，还要求没有 active Turn、没有 outstanding durable sleep、没有等待触发执行的 mailbox 项。没有输出不等于可回收。停止运行体后，回收路径提取未处理邮件放到运行时邮箱，保存环境选择，再移除驻留实例；身份登记仍用于后续恢复。

```text
B 完成一轮 → 空闲回收 → A 补派任务 → 加载 B → 开始后续执行
```

这是同一运行服务中的卸载与重载机制，不能推断所有邮箱都跨机器重启持久保存。发送普通消息与触发任务仍遵循[课程 0021](0021-subagent-message-delivery-and-execution.md)的区别。

入口：[residency.rs](../../../codex-rs/core/src/agent/control/residency.rs)。durable sleep 的生产触发链路尚未定位，已在课程 0021 单独记录证据边界，不作为普通调研流程前提。

## 显式关闭与归档为什么相似却不同

close_agent 尝试在持久父子关系中记录 Closed，再关闭目标及内存协作树可达的活跃后代。shutdown_live_agent 会处理历史落盘、发送 Shutdown、等待终止，并移除运行登记、驻留记录和邮箱。不同持久化失败分支有不同处理，不能说返回成功必然证明所有关系记录都落盘成功。

归档没有调用 close_agent。App-server 的 thread_archive_response 获取目标及派生子树，对运行体调用 prepare_thread_for_archive / prepare_thread_for_removal，再调用存储层 archive_threads。准备步骤移除客户端运行登记并请求 Shutdown；关闭超时或提交失败会记录日志后继续归档，不能用归档结果证明所有底层执行都已完全停止。

关闭处理协作使用关系，归档处理对话存储管理。源码还明确考虑“协作可能恢复已归档的后代，而不取消归档状态”，所以归档不等于永久销毁或封禁执行。关闭与归档都不是删除所有历史，更不是撤销外部副作用。

入口：[关闭实现](../../../codex-rs/core/src/agent/control/legacy.rs)、[归档及运行体移除](../../../codex-rs/app-server/src/request_processors/thread_processor.rs)。

## 回看时的判断方式

遇到“Agent 停了”先问：当前 Turn 是否结束？运行体是否仍驻留？协作身份是否保留？对话是否归档？不要让单个状态值回答四个问题。B 返回最终答案只说明这一轮结束，仍可继续交付后续任务。
