# 0036：执行异常后，从当前事实恢复

本课承接[取消与进程生命周期](0017-cancellation-and-process-lifetimes.md)，聚焦编码 Agent 在超时、取消或连接中断后如何继续工作。依据当前分支静态阅读；没有运行异常注入实验，也不表示独立工程已实现自动恢复。

## 一个贯穿场景

Agent 执行“生成代码，再运行测试”。生成步骤已修改文件，测试尚未完成，工具调用随后中断。此时不能只给整个任务贴一个“失败”标签，因为至少有三种状态需要分别判断：

- 执行状态：进程仍在运行、已退出，还是无法确认？
- 修改状态：文件未变、已全部改变，还是只完成一部分？
- 验证状态：检查未开始、执行中断，还是已有完整结果？

“进程已终止、文件已改变、验证未完成”完全可能同时成立。执行失败不意味着没有副作用；终止进程也不是回滚文件的机制。如果把这些状态合并，就容易重复修改、误报成功，或误删需要保留的工作。

## 暂时返回与真正超时

交互式执行可以在等待一段时间后返回当前输出和可续接的进程标识，命令仍可能运行。这里结束的是本次等待，而不是命令生命周期。模型应结合返回状态决定是否继续读取，不能因为尚未收到退出码就直接重启一份命令。

OneShot 则不向调用方交付可续接的进程。当前 `process_manager.rs` 在完成等待后检查进程是否退出；如果尚未退出，标记超时并调用 `terminate_confirmed`。终止出错时还有失败处理，不能把“发起终止”说成无条件证明所有外部活动均已停止。

`oneshot.rs` 的取消路径通过已发布的确切进程句柄尝试终止进程，并处理输出流取消或尚未取得句柄的情况，最终返回取消错误。它解决本次执行生命周期，不自动撤销已经写入的文件。

交互式进程与 OneShot 的取消契约不同，不能将其中一种行为推广到所有命令。更不能仅依据进程进入了管理器，就推断它一定跟随 Turn 中断而退出。

## 缺少结果不等于没有执行

连接断开可能发生在写文件之后、返回结果之前。宿主重启后，旧历史中的进程标识也不能单独证明那个进程仍可续接。

例如，“向文件追加一行”的命令其实已经完成，但成功结果没有被收到。盲目重放会追加两次。相比之下，某些操作重复执行可能得到相同最终效果，但这需要依据操作自身语义判断，不能从“这是 shell 命令”或“这是测试”直接得出。

合理的恢复顺序是先核对可获得的事实：仍可查询的进程状态、文件当前内容、差异、日志与完整检查结果。再判断已经完成的部分和剩余动作。无法确定的部分保留为“结果未知”，而不是自动归为“未执行”。

这是一种模型应采用的恢复策略，不代表当前 Harness 会为任意命令自动推断副作用或保证安全重试。

## 宿主能力与模型判断

| 宿主提供的能力 | 模型需要作出的判断 |
| --- | --- |
| 进程标识、输出、退出状态与终止机制 | 继续等待、停止还是检查结果 |
| 文件读取、差异与可用历史 | 已发生哪些修改，哪些属于当前任务 |
| 再次执行工具 | 重试是否会重复产生副作用 |
| 执行检查与测试 | 现有证据覆盖哪些要求，还缺什么 |

若产品需要强制保证异常后自动安全恢复，就应针对目标操作设计可持久化的操作记录、去重或事务等机制。这些是可选工程设计方向，不是本课已确认的 Codex 通用保证，也不是给独立工程自动新增的实施要求。
