# 从只读理解到编码执行：工具与权限的职责边界

本课回答：Agent 开始修改代码时，原有模型—工具循环增加了哪些责任，为什么面向 Agent 的专用修改工具仍应建立在通用权限与执行设施上？建议难度中高；记住职责、状态与失败后果，不要求背符号。本文保存已经讲解的内容，不是 CodebaseAgent 实现方案或转型实践任务书。

## 1. 编码任务的终点发生了什么变化

贯穿场景：用户要求修复函数处理空输入时的崩溃，并验证原有行为；工作区还有用户尚未提交的修改。

只读分析可以以有依据的原因解释结束。编码任务还需要实际变更、符合需求的行为、验证证据，以及准确说明完成范围。避免崩溃不能单独定义正确行为：空输入时返回零、返回空结果或返回错误，可能具有不同业务含义。先从接口约定、调用方和测试查找依据，仍有关键歧义时再澄清。

已有模型—工具循环继续适用：读取代码与测试 → 判断预期行为 → 提出修改 → 工具执行并回传结果 → 验证 → 修正或交付。这是任务推进关系，不要求宿主将步骤硬编码为固定流程。

必须分开四个状态：模型生成补丁表示提出请求；工具成功表示相应修改发生；验证通过提供特定范围的行为证据；任务完成还要判断证据是否覆盖用户目标。模型负责根据任务与结果决定下一步，运行时落实请求与约束，执行设施产生真实结果。

## 2. 权限、审批与执行结果

用户任务意图、当前有效授权、实际执行限制分别承担不同职责。已有授权覆盖的操作不必重复询问；不足时按当前审批策略决定申请或拒绝。获得授权并不保证执行成功，执行成功也不保证业务行为正确。

结构化补丁通常能提前提取目标路径；任意脚本的全部访问行为难以仅从命令文本得知。工作目录不是访问边界，测试也可能写入文件或启动子进程。因此，通用命令执行仍需要执行环境约束实际访问。

同一资源操作不能仅因换工具入口而获得额外权限。Skill 提供执行方法，不因此授予脚本新的权限；指令最终使用何种工具，就经过对应的执行链路。

审批通过后仍可能遭遇内容变化、写入失败或部分修改。取消任务也不会自动撤销已经发生的文件变化；验证未完成时不能宣称修复已验证，进程是否停止需要实际执行状态。撤销自身是新的修改，必须考虑用户已有工作。

## 3. Patch 是一种工具，不是所有修改的统一入口

Patch 是描述文件变更的文本，Codex 的 `apply_patch` 理解自己的补丁格式并执行新增、更新、删除等操作。Python 脚本、格式化工具、编译器同样可以产生文件变化，它们不会全部转换成补丁。因此，`ApplyPatchRuntime` 不能被理解为所有写入的统一安全关卡。

职责示意：

```text
apply_patch → 解析补丁、提取目标、准备审批 → 文件系统操作与执行后端
exec_command → 准备命令、审批与执行环境 → 进程及其实际资源访问
```

文件系统接口可以用路径、内容、权限上下文表达写入，而不关心内容是否来自补丁。当前 [LocalFileSystem](../../../codex-rs/exec-server/src/local_file_system.rs) 的 `write_file` 根据沙箱上下文选择文件系统执行后端。外部程序不必经过这个 Rust 方法，因此文件系统接口检查不能代替进程执行环境的约束。

## 4. 为什么仍有补丁专用类与前置检查

底层资源访问不负责解析补丁、定位文本、组织多个变更、准备变更展示或记录部分应用结果。这些操作语义需要具体工具实现。`execute_verified_patch` 是函数，`ApplyPatchRuntime` 才是具体运行时类型；带有 patch 的命名表达其操作职责。

| 入口或类型 | 职责 |
| --- | --- |
| [execute_verified_patch](../../../codex-rs/core/src/tools/handlers/apply_patch.rs) | 提取路径、结合环境与已有授权、准备请求和事件、调用执行编排、收集实际变更 |
| [prepare_apply_patch](../../../codex-rs/core/src/apply_patch.rs) 与 [assess_patch_safety](../../../codex-rs/core/src/safety.rs) | 根据补丁和策略形成自动允许、审批或拒绝的决定 |
| [ToolOrchestrator](../../../codex-rs/core/src/tools/orchestrator.rs) | 协调审批、沙箱选择及拒绝后的重试流程 |
| [ApplyPatchRuntime](../../../codex-rs/core/src/tools/runtimes/apply_patch.rs) | 实现具体补丁执行，将权限上下文传入文件系统操作并收集结果 |

这里的 `verified` 不表示全部权限已批准或业务已验证。前置补丁校验与授权、真实执行分别发生。`prepare_apply_patch` 的自动允许结果可以是 `Skip { bypass_sandbox: false, ... }`：无需额外审批，仍保留执行限制。

前置判断用于提前处理授权和展示完整操作；执行限制约束真实访问。`assess_patch_safety` 特别说明，路径位于可写范围内仍可能涉及硬链接等问题，不能以路径预检查替代实际限制。共享路径匹配与权限规则应复用；提取补丁目标、解释变更和准备交互是工具特有职责。此处说明实际分工，不宣称现有拆分已是最佳设计。

命令入口识别到可解析的补丁调用时，`intercept_apply_patch` 可将其接入同一补丁执行函数；这不意味着能够识别任意脚本的所有写入。

## 5. 面向 Agent 的场景特化

用户提出 agent native 的理解：Agent 是工具使用者，局部文件修改是编码场景中的常见操作，提供专用接口可以降低使用成本。

对比三种表达：重写整个文件需要携带大量无关内容；生成修改脚本需要处理查找替换、转义和脚本语法；补丁可以直接表达文件、上下文与局部变化。便利性主要指表达步骤与出错机会的减少，不代表已测得底层运行速度最快。

收益是双向的：模型更直接地表达修改意图，宿主更容易提取目标、展示差异、准备审批和追踪结果。其层次是：具体任务（修复空输入崩溃）→ 任务操作（应用补丁）→ 基础操作（读取、写入、删除文件）。它特化了操作方式，没有绑定金融、游戏等具体业务。

这是对设计收益的分析，不是 Codex 工具调用频率统计或历史设计动机的实证。专用工具是否值得存在，需要看表达成本、执行可靠性和结果可观察性收益，不能仅凭高频机械增加类型。
